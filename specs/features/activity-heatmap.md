# Feature: Daily practice activity and contribution graph

Status: Agreed (Umair, via the M9A.2 brief; no teammate sign-off)
Owner: Umair
Related: `specs/features/streak.md`, `specs/features/dashboard-page.md`,
`specs/00-product.md` § How users see progress

## Why

A learner returns more when daily practice leaves a visible record. Each day's
real practice becomes a shaded square on a twelve-month graph, so a habit is easy
to see and a gap is honest. The graph shows ACTUAL PRACTICE ACTIVITY only. It is not
a measure of proficiency and not a verified result, and it says so. It is built
as a reusable component so a later public profile can show it too.

## User stories

- As a learner, I want to see which days I practiced and how much, so that I can
  keep a daily habit going.
- As a learner, I want the graph and my streak to agree, so that I can trust both.

## Acceptance criteria

- **AC1** — GIVEN a UTC day THEN its activity is the learner's _qualifying_
  attempts on it, by the same rule as the streak (`streak.md` AC4: completed and
  not judged untouched-starter by the server). It records the qualifying run
  count, the distinct problems practiced and the distinct problems solved (a
  qualifying run that passed every test; a re-solve counts on the day it
  happens). Failing meaningful runs and reattempts of solved problems count.
- **AC2** — GIVEN many qualifying runs on one UTC day THEN the day appears once.
  The run count sets its shade; it never adds a streak day.
- **AC3** — GIVEN the graph and the toolbar flame THEN they are built from the same
  read of the same days: a day is shaded if and only if it is a streak day, and the
  current and longest streak are computed from exactly those days.
- **AC4** — GIVEN attempts saved before `Attempt.meaningful` existed (null) THEN
  they appear in the graph exactly as they count for the streak. History from
  before the feature is shown; nothing is backfilled or rewritten.
- **AC5** — GIVEN the Overview THEN a "Practice activity" card shows the last 365
  UTC days ending today: week columns (Sunday first), seven weekday rows, month
  labels over the week holding the 1st, and a Less–More legend. Inactive days are
  a neutral wash of the text colour; active days use four green levels with fixed
  thresholds: 1 run, 2–3, 4–6, 7 or more.
- **AC6** — GIVEN a day THEN it is reachable by mouse and keyboard and has a text
  label (date, runs, problems, solved, or "no practice"). The grid has one tab
  stop; arrow keys move between days and Home/End jump to the row's ends. The same
  detail is shown in a live line under the graph, not only in a tooltip.
- **AC7** — GIVEN a narrow screen THEN the graph scrolls inside its own box with the
  newest weeks in view; the page does not scroll sideways.
- **AC8** — GIVEN no qualifying activity THEN the graph shows neutral squares and
  says no practice has been recorded yet. GIVEN the read failed THEN the card says
  it is unavailable and draws no graph (never an empty-looking graph). GIVEN it is
  loading THEN a same-size placeholder is shown, announced as busy.
- **AC9** — GIVEN a signed-out visitor THEN no card is shown.
- **AC10** — GIVEN the card THEN it states that it shows practice activity, not
  skill or a verified result.

## Data / API

- Derived, not stored. `Attempt` stays the only source of truth: one read,
  `getActivitySummary()` (`src/server/learning/activity.ts`), selects `createdAt`,
  `status`, `meaningful`, `problemSlug` and `allPassed` of the learner's completed,
  not-`meaningful = false` attempts in the supported window (730 days), scoped to
  the session user and wrapped in React `cache` so the flame and the graph share
  one query per request. `getStreakSummary()` is built on it.
- Why no `activity_days` table: a counter table adds write-path coupling, drift
  and a historical backfill for a read that is one indexed query over a few
  columns today. Deriving means a retry or concurrent write can never add a streak day, and
  all history shows with no backfill. It is not full write idempotency: see the
  duplicate-attempt limit in Edge cases. A rollup becomes worth it when attempt volume makes
  this read slow; the pure `buildDailyActivity` output is its shape.
- Schema: one index, `Attempt @@index([userId, createdAt])`, for that read. The
  migration is generated by CI. No new table, no RLS change.
- Pure modules: `src/lib/activity/` (`daily-activity.ts`, `heatmap-grid.ts`,
  `activity-query.ts`). Component: `src/components/activity/`.

## Edge cases

- Empty / first-time: AC8. No fabricated squares or counts.
- 23:59:59 UTC and 00:00:00 UTC are different days; month, year and leap-day
  boundaries are ordinary days.
- A learner with more than 730 days of history sees the supported window.
- Before the `meaningful` migration runs the read falls back to counting every
  completed attempt (as the streak does).
- A duplicate persisted attempt (for example a browser retrying `saveAttempt` after
  a timeout, which stores a second `Attempt` row) counts as an extra run, so it can
  darken that day's shade by one step. It never creates a second streak day or
  changes the streak. `saveAttempt` is not idempotent per request; the graph does
  not hide that.
- Unauthenticated or another user's data: the user id comes only from the session.
