## Why

Learners who fail a problem guess-and-resubmit; M6 already turns their recorded
activity into a deterministic, evidence-tagged picture (`getLearningAnalytics()`),
but nothing tells the learner **what to do next**. M7 combines that picture with
a bounded structural read of the Python they actually wrote (via AST, never
executed on the server) to recommend which problem and which concept to practise
next, and — for learners who opt in — nudges them back with a daily email. It
serves "learning that sticks" by pointing at the specific gap the records show,
not a generic "try again".

## Scope and non-goals

### In scope (hackathon slice)

- A **deterministic recommendation engine** ranking the existing static catalog
  (`two-sum`, `contains-duplicate` only) and choosing focus concepts.
- **AST code-features** extracted in the browser Pyodide worker (`ast.parse`,
  no execution), persisted per attempt; **lazy, browser-driven backfill** of up to
  **10 historical (M4) attempts per browser session** — no resubmission required.
- A **bounded per-problem attempt sequence of the latest 5 attempts** (not just
  the latest) so M7 can tell a recurring mistake from a corrected one.
- **Optional AI diagnosis** via OpenRouter (`qwen/qwen3-coder-30b-a3b-instruct`),
  validated against the evidence, cached, with a deterministic fallback.
- A recommendations **card on the existing `/progress` page**.
- **Unified learning notifications (M7.5B, ADR-0004):** a persistent **in-app
  notification inbox** (bell in the header, default ON) and **opt-in daily email
  reminders** via Resend (default OFF), both rendered from one shared, deterministic
  reminder plan and produced by one daily scheduler, with a durable,
  concurrency-safe delivery ledger and inactivity-aware copy.

### Non-goals (v1)

- No new problems invented; the catalog stays the two static `PROBLEMS`.
- No server-side Python execution, ever (ADR-0001 holds).
- No raw learner source sent to OpenRouter (bounded AST + M6 evidence only).
- No cross-learner / instructor / cohort recommendations.
- No AI call on submit, replay, page load, or in the email cron.
- No webhook-confirmed email delivery tracking — we record **accepted by the
  provider**, not **delivered** (see Email).
- No per-user local send-time targeting; a single daily Vercel Hobby cron cannot
  honour per-user hours (see Email).
- No reminder cadence other than **daily** in v1.
- No browser push (service worker / Web Push) in v1 — the delivery ledger's
  `channel` column and the shared planner keep it a later, additive change.
- No notifications on submissions or test failures — at most one reminder per
  channel per day, from the scheduler only.
- No M8 / M9 implementation; their contracts are reused, not their code (below).
- No change to `RunResult` / `TraceResult` (decision #1).

### Forward compatibility (M8, M9)

`CodeFeatures` and `RecommendationEvidence` are the stable, provider-agnostic
evidence layer that M8 (problem-specific tutor) and M9 (adaptive learning) will
read later. To keep them reusable without building those modules now: the
evidence assembler (M7.2) stays pure and carries no recommendation-only
assumptions, `CodeFeatures` is versioned (`v`) so a later module can widen it
additively, and nothing in the evidence shape encodes a ranking decision. No
M8/M9 code, tables, prompts, or endpoints ship in M7.

## Module boundaries (M7.1–M7.5)

```
SUBMIT (browser)                                                   [no AI]
  Pyodide worker: run tests  ──then──▶ ast message → CodeFeatures
       practice-workspace ──saveAttempt({..., codeFeatures})──▶ attempts.codeFeatures

BACKFILL (browser, lazy, ≤10/session)              [no AI, no server Python]
  practice page opens (signed in) → listBackfillCandidates(limit) → worker ast per source
       → saveCodeFeatures(attemptId, features)   (idempotent, only where null)

GENERATE / REFRESH (server)                          explicit refresh OR dashboard-if-stale
  getLearningAnalytics() ─┐
  attempt sequences    ───┼─▶ M7.2 buildEvidence ─▶ M7.3 rank (deterministic, always)
                          │                           │ evidence changed & refresh-claim won?
                          │                           └─▶ M7.4 OpenRouter → Zod + evidence-check
                          └──────────────────────────────▶ upsert recommendation_cache

READ
  /progress card ──reads──▶ recommendation_cache (deterministic always; diagnosis only if fresh)
  daily cron     ──reads/computes──▶ recommendation_cache ──▶ Resend  (NO OpenRouter call)
```

- **M7.1 — Code evidence.** `src/lib/trace/code-features.ts` (pure projection of
  a Python-emitted structural summary) + an additive `ast` worker message
  (`buildWorkerSource`), returning `CodeFeatures`. Client calls it after a
  successful run and on backfill; `saveAttempt` / `saveCodeFeatures` persist it.
  **Structural facts only** — counts, booleans, a builtin allowlist. No claim of
  correctness, complexity, or mastery (adjustment B).
- **M7.2 — Evidence assembler.** Three pure modules and one server loader.
  `solution-evolution.ts`: `buildAttemptSequences(records)` turns stored attempt
  outcomes + fingerprints (never source) into per-problem `AttemptSequence`s.
  `recommendation-evidence.ts`: `buildRecommendationEvidence(analytics, sequences,
catalog, { generatedAt? })` joins M6 output, the sequences and the catalog into
  `RecommendationEvidence`, observed and inferred kept apart (adjustment B).
  `evidence-hash.ts`: `computeEvidenceHash(evidence)`. The loader
  `src/server/learning/recommendation-evidence.ts` (`getRecommendationEvidence()`)
  reads only outcomes, failed test ids and the fingerprint, scoped to the session
  user, and degrades like `getLearningAnalytics`.
- **M7.3 — Deterministic engine.** `src/lib/learning/recommend.ts`, pure:
  `rankRecommendations(evidence)` → `Recommendation` with `diagnosis.source:
'fallback'`, and `evidenceHash(evidence)`. **Always** produces a complete
  result; this is the source of truth and runs server-side with no browser and no
  Python, so the cron can call it too.
- **M7.4 — AI diagnosis.** `src/server/ai/openrouter.ts` (the only file importing
  the provider SDK / calling `trackAiCall`, per `docs/rules/ai-usage.md`) +
  `src/server/learning/recommend-ai.ts`. Takes M7.3 output + evidence, asks for a
  short diagnosis, validates with Zod **and** against the evidence, attaches on
  success, drops to fallback on any failure.
- **M7.5A — Persistence + refresh + card.** `src/server/learning/recommendation-cache.ts`
  (pure policy), `src/server/learning/recommendation.ts` (`getRecommendation`,
  `refreshRecommendation`, `recommendationForUser`), the `/progress` card.
- **M7.5B — Notifications.** `src/lib/learning/reminder-plan.ts` (shared planner
  and copy), `src/server/notifications/scheduler.ts` (pure scheduler) +
  `daily-reminders.ts` (Prisma/Resend wiring), `inbox.ts` (session-scoped inbox
  and preferences), `src/server/email/resend.ts` (the Resend wrapper),
  `src/lib/notifications/*` (email config gate, email template, query builders),
  the bell in `SiteHeader`, preferences on `/progress`, `/unsubscribe`, and
  `GET /api/cron/learning-reminders` (`createCronRoute`).

## Typed data contracts

Design sketches (Zod schemas live in `src/lib/learning/` at build time). All are
**bounded**: counts/enums/booleans and short, capped, allow-listed string arrays —
never raw identifiers, so nothing here is PII.

```ts
// M7.1 — persisted on each attempt (attempts.codeFeatures). Versioned, normalized.
type CodeFeatures = {
	v: 1
	loops: { for: number; while: number; maxDepth: number }
	comprehensions: number
	branches: number // if / elif nodes
	returns: number
	defs: number
	recursion: boolean // a def references its own name
	usesDict: boolean
	usesSet: boolean
	usesSorted: boolean
	builtinCalls: string[] // from a fixed allowlist (len/range/enumerate/…), sorted, ≤16
	nodeCount: number // AST node count (size proxy, NOT a complexity claim)
	lineCount: number
}
// What the worker's `ast` message returns. A source that doesn't parse, or can't
// be analysed, is a VALIDATED outcome (never a throw); no features are stored for it.
type AstResult =
	| { status: 'ok'; features: CodeFeatures }
	| { status: 'syntax_error'; syntaxError: { message: string; line: number; column: number } }
	| { status: 'analysis_error'; message: string; permanent: boolean }
// permanent: too large / parser limit (the same source always fails);
// not permanent: timeout or dead worker (worth retrying later).

// What the column holds instead for a source that can never be analysed.
type UnanalyzableMarker = { v: 1; unanalyzable: 'syntax_error' | 'not_analyzable' }

// A pre-M7 or not-yet-backfilled attempt stores null. Readers use
// parseStoredCodeFeatures(value): null / corrupt / other-version → null, never an error. "Normalized" = canonical
// field order and sorted arrays, so equal content serialises identically (feeds
// the evidence hash below).

// M7.2 — solution evolution (src/lib/learning/solution-evolution.ts). Everything
// here is OBSERVED. Window = the latest 5 attempts of one problem, oldest first.
type AttemptSeqItem = {
	order: number // 1-based within the window
	attemptId: string
	createdAt: string
	runStatus: 'completed' | 'syntax_error' | 'timeout' | 'engine_error' | 'other'
	outcome: 'passed' | 'failed'
	testsPassed: number
	testsTotal: number
	failedTestIds: string[] // sorted, unique
	code: CodeFeatures | null
	codeStatus: 'features' | 'unanalyzable' | 'missing'
	sameStructureAsPrevious: boolean | null // null when either lacks a fingerprint
}
type StructuralChange =
	// between two CONSECUTIVE attempts that both have a fingerprint
	| 'nested_loops_added'
	| 'nested_loops_removed'
	| 'loop_depth_increased'
	| 'loop_depth_decreased'
	| 'dict_introduced'
	| 'dict_removed'
	| 'set_introduced'
	| 'set_removed'
	| 'sorted_introduced'
	| 'sorted_removed'
	| 'recursion_introduced'
	| 'recursion_removed'
type StructuralTransition = {
	change: StructuralChange
	fromOrder: number
	toOrder: number
	fromAttemptId: string
	toAttemptId: string
	outcomeChange: 'failed_to_failed' | 'failed_to_passed' | 'passed_to_failed' | 'passed_to_passed'
	// co-occurs with the change; never claimed to be caused by it
}
type PatternStatus = 'no_evidence' | 'absent' | 'appeared_once' | 'recurring' | 'disappeared'
type StructuralPattern = {
	feature: 'nested_loops' | 'dict' | 'set' | 'sorted' | 'recursion'
	status: PatternStatus
	presentIn: number
	of: number // fingerprinted attempts that have it / all fingerprinted
	inLatest: boolean | null
	droppedWithFailToPass: boolean // a removal coincided with a failed → passed change
}
type AttemptSequence = {
	problemSlug: string
	windowSize: number
	items: AttemptSeqItem[] // at most 5
	coverage: { attempts: number; withFeatures: number; unanalyzable: number; missing: number }
	transitions: StructuralTransition[]
	patterns: StructuralPattern[]
	contradictions: {
		kind: 'inconsistent_attempt_record' | 'same_structure_different_outcome'
		attemptIds: string[]
	}[]
}

// M7.2 — the evidence (src/lib/learning/recommendation-evidence.ts). Observed and
// inferred are separate fields at every level. M7.2 infers NOTHING of its own: the
// inferred side is M6's signals and insights, re-filed unchanged. There is no
// mastery score, no "struggling" flag, and no claim that a structural change
// improves a solution.
type RecommendationEvidence = {
	v: 1
	generatedAt: string | null // volatile — EXCLUDED from the fingerprint
	hasActivity: boolean
	totals: LearningStatistics['totals'] // M6
	problems: ProblemEvidence[] // every catalog problem + any other with history, by slug
	concepts: ConceptEvidence[] // one per catalog concept tag, by tag
	insights: { observed: InsightRef[]; inferred: InsightRef[] } // account-wide, from M6
}
type ProblemEvidence = {
	slug: string
	known: boolean // false: history on a problem the catalog no longer has
	conceptTags: string[]
	difficulty: 'easy' | 'medium' | 'hard' | null
	progress: 'not_started' | 'attempted' | 'solved' // a status, not a mastery claim
	observed: {
		// M6 statistics + behaviour, reused as-is
		attempts: number
		passedAttempts: number
		failedAttempts: number
		solved: boolean
		attemptsToFirstSolve: number | null
		latestOutcome: 'passed' | 'failed' | 'none'
		latestPassFraction: number | null
		bestPassFraction: number | null
		trend: ImprovementTrend
		stepImprovements: number
		longestFailureStreak: number
		failurePattern: FailurePatternAnalysis
		scoreChanges: ScoreChangeAnalysis
		hints: HintCounts
		replay: ReplayEngagement
		windowCoversAllAttempts: boolean
		sequence: AttemptSequence // M7.1 fingerprints + M7.2 evolution
		insights: InsightRef[] // M6 insights tagged `observed`
	}
	inferred: {
		signals: InferredSignal[] // M6, each `basis: 'inferred'`
		insights: InsightRef[] // M6 insights tagged `inferred`
	}
}
type ConceptEvidence = {
	tag: string
	problems: string[] // catalog problems carrying the tag
	observed: {
		problemsInCatalog: number
		problemsAttempted: number
		problemsSolved: number
		problemsWithRepeatedFailures: number
		problemsWithOpenRepeatedFailures: number
		structuralPatterns: Record<StructuralFeature, Record<PatternStatus, number>>
	}
	inferred: { signals: Partial<Record<InferredSignalCode, number>> }
}

// M7.3 (+ M7.4) — one cached object, reused by dashboard and email.
type Recommendation = {
	v: 1
	generatedAt: string // volatile — EXCLUDED from evidenceHash
	evidenceHash: string // see "cache invalidation" below
	focusConcepts: string[]
	rankedProblems: { slug: string; score: number; reasonCode: string; reasonText: string }[]
	diagnosis: {
		source: 'ai' | 'fallback'
		stale: boolean // true if this diagnosis was produced for an older evidenceHash
		summary: string // ≤ 280 chars
		nextStep: string // ≤ 160 chars
		claims: { problemSlug: string | null; metric: string }[] // each must exist in evidence
	}
}
```

## Historical attempt handling (adjustment A)

M4 already holds `source` for past attempts with no `codeFeatures`. The server
must never run Python, so backfill is **browser-driven, lazy, and bounded**:

- On practice-page open, once Pyodide is warm, a client task calls `listBackfillCandidates({ limit })` — a session-scoped action
  returning up to `limit` (default and hard cap **10**) of the learner's **own**
  recent attempts whose `codeFeatures` is null, each with its `source`. Attempts
  recorded with status `syntax_error` are never candidates (they can never
  parse, so they would otherwise be re-listed every session).
- **Practice page only.** ADR-0001 keeps Pyodide off every page but the problem
  page, and loading ~14 MB of Python to backfill from `/progress` would break
  that, so the earlier "also on dashboard open" trigger was dropped.
- **The 10-per-session budget** is kept in `sessionStorage` (per tab, survives a
  reload) with an in-memory mirror, so blocked storage degrades to a per-page-load
  bound, never an unbounded one. Each attempt is counted when it is analysed, so
  a source that always fails still uses its slot. The pass waits for the engine to
  be idle (a learner's own Run/Replay is never delayed by more than one parse),
  stops if the page unmounts, and swallows every failure.
- **Source is only ever returned to its owner.** The action is scoped by the
  session user id (never the body), returns at most 10 rows, only for attempts
  that actually need features, and does not page through the whole history. RLS
  backstops it. No endpoint returns another learner's source, and no bulk source
  export exists.
- For each candidate, the client runs the `ast` worker message and posts the
  result via `saveCodeFeatures(attemptId, features)` — ownership-checked,
  idempotent, sets only where currently null.
- **Final failures are recorded, so they are processed once.** A source that
  can never be analysed (it does not parse, or exceeds the limits —
  `analysis_error` with `permanent: true`) gets a small marker stored in the same
  `codeFeatures` column (`{ v: 1, unanalyzable: 'syntax_error' | 'not_analyzable' }`).
  It is no longer null, so it is never listed, downloaded or parsed again, and a
  pile of such attempts cannot hold the newest-first queue hostage (a regression
  test replays four sessions against twelve of them). Readers treat the marker as
  "no features" (`parseStoredCodeFeatures` → null). Retryable failures (timeout,
  dead worker) store nothing and **end the pass** rather than burning the budget.
- **The backfill never boots Pyodide.** It starts only when the worker is already
  booted (after the practice page's warm-up), re-checks before every item, and
  stops if the worker was recycled, so a background pass can never make a
  learner's Run wait behind a runtime reload.
- **The features describe exactly the saved source.** New attempts are analysed
  from the very `source` string that is saved (`withCodeFeatures`); backfilled
  features are keyed by the attempt id the server returned that source for. The
  server cannot re-parse to check (it never runs Python), so a client could store
  features that don't match its own source; that only affects that learner's own
  recommendations, which is the same trust model as client-reported pass/fail
  (ADR-0001).
- **Every layer tolerates `code === null`**: sequences, evidence, ranking and the
  AI prompt all degrade to M6 test-outcome signals when features are absent. No
  learner is ever asked to resubmit.

## Recommendation generation and cache invalidation

- `recommendation_cache` holds one row per user: the full `Recommendation`, plus
  `evidenceHash`, `model`, `diagnosisSource`, `generatedAt`, and the refresh-claim
  fields below.
- **`evidenceHash` is content-addressed** (adjustment 1). It is
  `ev1:` + the SHA-256 of the **canonical JSON** (keys sorted at every level,
  lists already normalised) of `{ fingerprint: 1, evidence }` with the volatile
  `generatedAt` removed (`evidence-hash.ts`). Because it covers the whole evidence
  it includes:
  - each in-scope attempt's outcome (`testsPassed`/`testsTotal`/`outcome`/
    `failedTestIds`/`runStatus`) **and its full normalised `CodeFeatures` content**
    (or its `missing`/`unanalyzable` status) — **not** merely `codeFeatures.v`;
  - the derived transitions, patterns and contradictions per problem;
  - the M6 statistics, behaviour, signals and insights it carries, and the
    catalog's tags and difficulty.
    It **excludes every volatile field**, including `RecommendationEvidence.generatedAt`
    and `Recommendation.generatedAt`, so re-reading unchanged data yields the same
    hash. The version prefix means a change to the evidence shape or the
    canonicalisation (bump `EVIDENCE_FINGERPRINT_VERSION`) invalidates everything
    cached, and an old hash can never be mistaken for a new one. Recording that a
    source can never be analysed (a marker) is a change in evidence and changes
    the hash too.
  - **Consequence that adjustment 1 requires:** a backfill that fills a
    previously-`null` feature set changes the hashed content **even though the
    attempt ids and the AST schema version are unchanged**, so the old evidence
    is invalidated and the recommendation (and any AI diagnosis) is refreshed.
- **Dashboard read:** if the cache is missing or its stored `evidenceHash` ≠ the
  freshly computed hash, M7.2+M7.3 run synchronously (pure, cheap) and the fresh
  deterministic result is shown and cached. The AI diagnosis is **not** computed
  on a plain page load.
- **Stale AI diagnosis is never shown as current** (adjustment 3). A diagnosis is
  stored bound to the `evidenceHash` it was produced for. On read, if that hash ≠
  the current evidence hash, `getRecommendation` returns the fresh deterministic
  ranking with `diagnosis.source: 'fallback'` and does **not** surface the old AI
  text as the latest analysis. The stale AI text is either dropped or, if shown at
  all, explicitly labelled stale (`diagnosis.stale: true`) and visually separated
  from the current result — never presented as describing the latest attempts.
- **Refresh (explicit):** the learner's "Refresh" action recomputes evidence +
  deterministic ranking and, if the evidence changed and the refresh claim is won
  (below) and AI is enabled, calls M7.4 and caches the validated diagnosis bound
  to the new hash. If AI is skipped or fails, the result stays deterministic.

## OpenRouter call triggers and cost limits (adjustments 4, C)

- **Model (implemented M7.4):** `nvidia/nemotron-3.5-super-vl:free` — a verified
  **free** ($0/token) OpenRouter model with native structured-output and reasoning
  support, registered in `OPENROUTER_SLUGS` (`src/server/lib/ai-usage/models.ts`).
  The spec's first candidate `qwen/qwen3.6-plus:free` does **not** exist upstream
  (only the paid `qwen/qwen3.6-plus`), and no free qwen model exists today, so this
  is the verified substitute — never a silent paid fallback. Configurable via
  `OPENROUTER_MODEL`, but only to another mapped slug (an unknown value falls back
  to this default, so a call can never ship unpriced). A `:free` model records a
  real $0 cost, not the NULL of an unmapped model (`pnpm check:ai-models` confirms
  it still prices; 7/7 mapped). Calls go only through `src/server/ai/openrouter.ts`,
  tracked with `feature: 'learning_recommendation'` (`_retry` for the one bounded
  retry), `provider: 'openrouter'` (M7.5A: its own attribution value, read with the
  OpenAI-compatible extractor since OpenRouter speaks that protocol), `meta` =
  ids/enums only. `max_tokens` ≤ 600, 20 s timeout, `temperature` 0.
- **The only triggers:** (1) explicit learner refresh; (2) — reserved — a future
  scheduled refresh. **v1 cron never calls OpenRouter** (adjustment C).
- **Concurrency-safe refresh claim** (adjustment 4) — not just a timer. To call
  the model for `evidenceHash = H`, a refresh must first **win a durable claim**:
  an atomic conditional write on `recommendation_cache`
  `SET refresh_state='running', refresh_claim_hash=H, refresh_claimed_at=now()
WHERE user_id=? AND (refresh_state IS DISTINCT FROM 'running' OR
refresh_claimed_at < now() - CLAIM_TTL)`. Only the writer whose statement
  affected the row makes the single OpenRouter call; a concurrent refresh for the
  same learner and the same `H` sees the live claim and makes **no** model call
  (it returns the current deterministic result). `CLAIM_TTL` (≈60 s) lets a
  crashed refresh self-heal. On completion the claim is released
  (`refresh_state='idle'`).
- **Other cost guards:** fire only when `evidenceHash` changed since the last
  diagnosis; a per-user minimum interval (≈10 min) as a secondary rate cap even
  across evidence changes; `max_tokens` bounded (≤600). **Never** on submit,
  replay, page load, or per-email.

### Hackathon release: in-app notifications only (2026-11-05)

This release policy overrides the email enablement and preference controls below
(including AC14–AC19 and AC23): all reminder preference controls are hidden in Settings, and
both cron reminder channels are disabled in code, independent of environment
configuration and existing opt-ins. No email delivery slots are claimed or retried
and Resend is never invoked. Daily recommendations, the bell, notification history
and spaced-review reminders remain operational, always enabled, including for previously opted-out learners.
Stored opt-ins, delivery tables, Resend integration, templates and unsubscribe
flows are preserved for future use. Supabase Auth, signup and password-reset
emails are unchanged. No infrastructure, environment variable or migration is added.

- **AC19a** — GIVEN valid email configuration and existing opt-ins (including
  retryable deliveries) WHEN the daily cron runs THEN eligible daily and due-review
  in-app reminders are created, no reminder email is sent and Resend is never called.
- **AC23a** — GIVEN Settings in this release THEN no reminder preference controls
  are visible. In-app reminders are always active, including for existing opt-outs.

### Enrichment diagnostics (M7.4 follow-up)

An enrichment that is dropped must be explainable without storing what the model
said. Every dropped enrichment — and only a dropped one; success and a missing key
are silent — emits one structured server log line (`log.warn`,
`docs/rules/logging.md`) and still the existing `captureError` report. The line is
built from `EnrichDiagnostics` (`src/server/learning/recommend-ai.ts`), which has
**no free-text field**: a `stage`, the existing rejection `reason`, and bounded
facts about the response.

| Field                         | Values                                                                             | Meaning                                                                                                                                                                                                                                              |
| ----------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `stage`                       | `provider` · `missing_content` · `invalid_json` · `schema` · `evidence`            | where the enrichment was dropped                                                                                                                                                                                                                     |
| `reason`                      | the existing `EnrichFailure` enum                                                  | `rate_limited`/`server_error`/`timeout`/`network_error` (provider); `invalid_response` (missing content); `invalid_json`; `schema_rejected`; `unknown_slug`/`unresolved_metric`/`wrong_metric_value`/`unknown_concept`/`disallowed_claim` (evidence) |
| `httpClass`                   | `2xx` · `4xx` · `5xx` · `other` · `none`                                           | `none` = no response (timeout, network)                                                                                                                                                                                                              |
| `finishReason`                | `stop` · `length` · `content_filter` · `tool_calls` · `error` · `other` · `absent` | OpenRouter's normalized finish reason                                                                                                                                                                                                                |
| `hasContent` / `contentChars` | boolean / count                                                                    | a non-empty `message.content` and its length                                                                                                                                                                                                         |
| `hasReasoning`                | boolean                                                                            | the model emitted reasoning (a reasoning field, details, or a reasoning-token count) — presence only, the text is never read out                                                                                                                     |
| `usageReported`               | boolean                                                                            | the provider itself gave both prompt and completion counts (versus our zero default)                                                                                                                                                                 |
| `requestId`                   | opaque id                                                                          | the provider's response id (only if it is a plain token), to join the line to its `ai_usage.request_id` row                                                                                                                                          |

The log line also carries the resolved `model`. `finishReason: 'length'` is a
**signal to look at the token budget, not a verdict**: the record deliberately has
no "cause" field, because a length stop and a rejection can both be effects of
something else. None of the prompt, the response text, the reasoning text, learner
source, names, emails, keys, session tokens or a provider error body can appear —
there is no field to carry them, a non-token `requestId` is dropped, and the
logger's redaction remains a backstop, not the mechanism. Diagnostics change
nothing about behaviour: the deterministic fallback, claim release, cooldown,
`max_tokens` (≤ 600), model and `ai_usage` tracking are exactly as above.

To inspect the next rejected response: find the `learning recommendation
enrichment skipped` line in the server's stdout (the `next dev` terminal locally,
the log drain in a deployment), read `stage`/`reason`/`finishReason`/`hasContent`/
`hasReasoning`/`usageReported`, and join on `requestId` to the `ai_usage` row for
tokens, latency and cost.

## Notifications: planner, in-app, email, scheduling (M7.5B — as implemented)

**Shared planner.** `planReminder(recommendation, evidence, catalog, now)` turns
the learner's current M7.3 recommendation into one enum-only `ReminderPlan`
`{ v: 1, template, problemSlug, reasonCode, conceptTag, inactiveDays }`. Templates:
`cold_start` (no saved attempt), `returning` (latest attempt ≥ 3 days old),
`unfinished` (top pick attempted, unsolved), `new_problem` (top pick untried while
other work exists), `revision` (everything solved). The problem is always the
recommendation's top pick — the planner never re-ranks — and an unknown slug yields
no plan, so no reminder can link to a missing page. `reminderCopy(plan, title)` is
the single source of the words for both channels; every sentence states a status
or a day count, never a judgement. No OpenRouter, no Python.

**Preferences** (`notification_preferences`, one row per learner, scoped by the
session id): `inAppEnabled` (default **true**), `emailOptIn` (default **false** —
explicit opt-in), `cadence` (`daily`), `unsubscribeToken` (256-bit random,
base64url, unique). The two channels are independent. A learner without a row is
treated as in-app on, email off. No per-user send hour or timezone.

**In-app.** `learning_notifications` rows, unique on `(userId, logicalKey)` with
`logicalKey = daily:<UTC date>`, inserted `ON CONFLICT DO NOTHING`. The payload is
the plan, rendered at display time; a payload that doesn't parse, or names a
problem the catalog no longer has, renders as a neutral pointer to `/progress`.
The bell shows the unread count (one indexed `COUNT` per page, behind
`<Suspense>`), loads the latest 20 on open, and supports mark-read and mark-all-read
— each a conditional `UPDATE … WHERE userId = <session> AND readAt IS NULL`.

**Email.** Sent only when `RESEND_API_KEY`, `REMINDER_FROM_EMAIL` and
`RESEND_VERIFIED_DOMAIN` are all set and the sender's domain equals the declared
verified domain (`resolveEmailConfig`, no network call) — a key alone never sends.
Content: title, the evidence-grounded reason, the concept, a practice link, and an
unsubscribe link; no source, trace or identifiers beyond the plan; HTML-escaped.
Headers `List-Unsubscribe` + `List-Unsubscribe-Post: List-Unsubscribe=One-Click`
point at `POST /api/notifications/unsubscribe?token=` (RFC 8058). The visible link
goes to `/unsubscribe?token=`, which asks for a confirming click so mail scanners
that prefetch links can't unsubscribe anyone. Unsubscribing sets `emailOptIn=false`
only and answers identically whether or not the token matched.

**Delivery ledger** (`notification_deliveries`, PK `(userId, deliveryDate,
channel)`; `channel` = `'email'`, `'push'` reserved):

- **Claim:** atomic insert `ON CONFLICT DO NOTHING` (`status 'claimed'`,
  `attempts 1`); otherwise one conditional `UPDATE` reclaims a `retry` row or a
  `claimed` row older than the 10-minute claim TTL (a crashed run), only while
  `attempts < 3`. Of two concurrent runs exactly one matches.
- **States:** `claimed → accepted | retry | failed`. `accepted` = Resend returned a
  message id; **never "delivered"** (no webhook in v1).
- **Retries:** a transient error (5xx, 409, timeout, network) gets one immediate
  in-run retry; a 429 marks the slot `retry` and stops email for the rest of the
  run (circuit breaker); a permanent rejection (other 4xx) is `failed`. Attempts are
  capped at 3 per slot. `lastError` holds a code, never a message or address.
- **Frozen payload:** the first claim stores the planned reminder (`{ plan,
problemTitle }`) in the slot's `payload`; retries and crash recovery re-send that
  exact copy, because Resend rejects a reused idempotency key carrying a different
  body rather than replaying it — and the learner's plan can change between a crash
  and its recovery.
- **Idempotency:** every send carries `Idempotency-Key: reminder:{userId}:{date}`.
  After a crash between "Resend accepted" and "we recorded it", the slot is
  reclaimed after the TTL and re-sent with the same key; Resend replays the
  original response within its retention window (24 h at the time of writing —
  **confirm against Resend's documentation before production**). Exactly-once
  end-to-end is not claimed.

**Scheduler** (`GET /api/cron/learning-reminders`, `CRON_SECRET` via
`createCronRoute`, one UTC schedule `0 15 * * *` in `vercel.json`,
`maxDuration = 60`): candidates are learners with in-app on (including no
preference row) or email opted in, at most 5,000, rotated deterministically per
date. Learners with nothing left to do today are skipped without planning. Each
remaining learner is planned from the deterministic recommendation read path
(`recommendationForUser`: cache reused when its hash matches, otherwise recomputed
and cached — **no OpenRouter, no Python**), then in-app and email are delivered
**independently** (one failing never blocks the other). The run stops _starting_
learners after 300 or 45 s and reports `truncated`; it is idempotent, so any later
invocation the same UTC day continues. The response and logs carry counts only.

**Vercel Hobby limitation (accepted, ADR-0004):** one daily invocation with a capped
duration. If more learners need work than fit in one run, the remainder waits for
another invocation that day (a second Hobby cron entry or a manual authenticated
call) or the next day. Delivery time is one fixed UTC hour; no local time is
promised.

## Edge cases

- **Empty / first-time:** no attempts → `getRecommendation` returns a
  deterministic "start with the easier problem" result; no AI call; no email slot.
- **No `codeFeatures` yet:** ranking + diagnosis run from M6 outcomes alone; the
  card and email render normally; backfill fills features over a few visits.
- **Backfill fills a null feature set:** the evidence content changes → hash
  changes → recommendation refreshes (adjustment 1), even with the same attempt
  ids and AST `v`.
- **AI off / down / invalid / unverified claim:** `diagnosis.source: 'fallback'`;
  `captureError`; dashboard and email unaffected.
- **Stale diagnosis:** an AI diagnosis whose `evidenceHash` no longer matches is
  never shown as the current analysis (adjustment 3).
- **Concurrent refresh:** two refreshes for the same learner and evidence → one
  wins the claim and calls the model, the other makes no model call (adjustment 4).
- **Unauthenticated / another user's data:** every action and server fn is scoped
  by the session user id; `saveCodeFeatures`/`listBackfillCandidates` only touch
  the caller's own attempts and return only the caller's own source; RLS backstops.
  `getRecommendation` returns `authenticated:false`.
- **DB unavailable:** `getRecommendation` returns `available:false` (mirrors
  `getLearningAnalytics`); never throws.
- **Concurrent cron runs / retries:** the `(userId, deliveryDate, channel)` unique
  slot + Resend idempotency key give at-most-once per user per UTC date; `accepted`
  ≠ delivered; crash window documented (adjustment 5).
- **Resend rejects / throws:** delivery row stays `claimed` with `attempts`
  incremented, retried next run up to `MAX_ATTEMPTS`, then `failed`.
- **Limits:** source analysed ≤ 20 000 characters; every count ≤ 100 000; ast
  timeout 2 s; attempt-sequence window 5; backfill ≤10/session; `builtinCalls` ≤16;
  `max_tokens` ≤600; refresh min-interval ≈10 min; claim TTL ≈60 s;
  `MAX_ATTEMPTS` 3.

## Acceptance criteria

- **AC1** — GIVEN a submitted solution WHEN it runs in the worker THEN an `ast`
  message returns a versioned `CodeFeatures` built by `ast.parse` (never executed),
  containing only counts/booleans and allow-listed builtin names, and
  `saveAttempt` persists it to `attempts.codeFeatures`. If the value fails the
  strict server-side schema it is dropped (and reported) and the attempt is saved
  without features: an AST problem can never cost a learner a submission.
- **AC2** — GIVEN the same source WHEN features are extracted twice THEN the output
  is byte-identical (deterministic, no clock/random), and arrays are sorted so
  equal content serialises identically.
- **AC3** — GIVEN a pre-M7 attempt with `codeFeatures = null` WHEN the learner
  opens a practice page while signed in THEN a client backfill of at most 10 of the
  learner's own attempts per session extracts and saves features, without
  resubmission and with no server-side Python. `saveCodeFeatures` writes only where
  null and only on the caller's own attempts.
- **AC4** — GIVEN several attempts on a problem WHEN evidence is built THEN an
  `AttemptSequence` of at most the latest 5 attempts (oldest→newest, ties broken by
  id, input order irrelevant) is produced with order, timestamps, outcomes, failed
  test ids, the fingerprint or its `codeStatus`, and observed transitions between
  **consecutive** fingerprinted attempts (a missing one is never bridged over).
- **AC5** — GIVEN a learner who moved from nested loops to a dict/set across
  attempts THEN the transitions record it as an observed fact
  (`nested_loops_removed` / `dict_introduced`) beside the outcome change, each
  structural fact is classed `recurring` / `appeared_once` / `disappeared` /
  `absent` / `no_evidence`, and no field asserts correctness, complexity, speed or
  mastery from AST alone; `observed` and `inferred` are separate fields and M7.2
  adds no inference of its own.
- **AC6** — GIVEN any evidence (including empty, or all-null features) WHEN the
  deterministic engine runs THEN it returns a complete `Recommendation` with
  `focusConcepts`, a ranked list over the two static problems only, and
  `diagnosis.source: 'fallback'` — no new problems invented, no AI required.
- **AC7** — GIVEN AI enabled, evidence changed, and the refresh claim won WHEN
  `refreshRecommendation` runs THEN OpenRouter is called once through
  `src/server/ai/openrouter.ts`, costed in `ai_usage` with
  `feature:'learning_recommendation'`, and the result is Zod-validated.
- **AC8** — GIVEN an AI diagnosis WHEN any claim references a `problemSlug`/metric
  not present in the evidence THEN the diagnosis is rejected and the engine falls
  back; a validated diagnosis's `claims` all exist in the evidence.
- **AC9** — GIVEN OpenRouter unset, erroring, timing out, or returning invalid JSON
  THEN `getRecommendation` still returns a deterministic result and the
  dashboard/email are unaffected; the failure is `captureError`-reported, not
  thrown.
- **AC10** — GIVEN `evidenceHash` is computed WHEN two reads see the same
  normalised feature content and outcomes THEN the hash is equal; WHEN a null
  feature set is later backfilled (same attempt ids, same AST `v`) THEN the hash
  changes and the cached recommendation is invalidated. Volatile `generatedAt`
  fields never affect the hash. A plain page load never calls AI.
- **AC11** — GIVEN raw learner source WHEN any OpenRouter request is built THEN the
  payload contains bounded `CodeFeatures` + M6 evidence only and never the source
  text or personal details; `ai_usage.meta` carries ids/enums only.
- **AC12** — GIVEN a stored AI diagnosis WHEN the current evidence hash differs
  from the diagnosis's hash THEN `getRecommendation` returns the fresh
  deterministic ranking and does not present the old AI text as the current
  analysis (dropped, or shown only with `stale: true` and separated).
- **AC13** — GIVEN two concurrent refreshes for the same learner and the same
  evidence THEN exactly one wins the durable claim and calls the model; the other
  makes no model call; a crashed claim expires after the TTL.
- **AC14** — GIVEN email reminders default off (in-app defaults on) WHEN a learner opts in THEN
  `notification_preferences` is created/updated for that user only; the unsubscribe
  token sets `emailOptIn=false` and nothing else. No per-user send hour or timezone is stored.
- **AC15** — GIVEN two concurrent cron runs for the same user and UTC date THEN
  exactly one claims the `(userId, deliveryDate, channel)` slot and sends; the
  other skips. An `accepted` row is never re-sent; a failed send is retried up to
  `MAX_ATTEMPTS`, then `failed`.
- **AC16** — GIVEN a send WHEN it is issued THEN it carries the idempotency key
  `reminder:{userId}:{deliveryDate}`; GIVEN a crash between Resend acceptance and
  persisting `accepted` THEN the next run's retry does not double-send (provider
  de-dupes). `accepted` is recorded, never `delivered`.
- **AC17** — GIVEN the daily cron runs THEN it calls no OpenRouter; for an opted-in
  user without a fresh cached recommendation it computes a deterministic one
  server-side (no browser, no Python) and sends from it.
- **AC18** — GIVEN an opted-in but inactive learner THEN a reminder is still sent
  (no new-activity gate) with inactivity-aware copy; daily cadence bounds
  frequency.
- **AC19** — GIVEN `REMINDER_FROM_EMAIL` not on a verified domain, or
  `RESEND_API_KEY` unset THEN no real send occurs and the cron no-ops cleanly.
- **AC20** — Every M7 read/write (preferences, recommendation, deliveries,
  features, backfill sources, notifications) is scoped by the session user id and
  can't be redirected by the body; new tables have RLS enabled with no policy
  (`pnpm check:rls`).
- **AC21** — GIVEN the daily scheduler runs for a learner with in-app enabled THEN
  exactly one `learning_notifications` row exists for `(userId, 'daily:<date>')`,
  however many times or concurrently it runs; no notification is created by a
  submission, a failed test, or a page load.
- **AC22** — GIVEN a signed-in learner THEN the header bell shows their unread
  count; opening it lists their latest notifications with links to real practice
  pages (or `/progress` for an unrenderable one); mark-read and mark-all-read touch
  only their own unread rows. Signed-out visitors see no bell.
- **AC23** — GIVEN preferences THEN in-app defaults on and email defaults off, each
  switchable independently; the unsubscribe token turns email off only, the
  visible unsubscribe link requires a confirming click, and the RFC 8058 endpoint
  answers identically for valid and invalid tokens.
- **AC24** — GIVEN a run that exhausts its budget THEN it reports `truncated`, and a
  re-invocation the same UTC day skips finished learners and continues.
- **AC25** — GIVEN an OpenRouter enrichment that is dropped (provider failure,
  missing/reasoning-only/empty content, invalid JSON, schema rejection, or any of
  the five evidence rejections) THEN exactly one structured log line records its
  stage, reason, HTTP class, finish reason, content/reasoning presence and whether
  usage was reported, contains no prompt, response, reasoning, source, email, key
  or token, and the deterministic recommendation is returned unchanged; a valid
  response and a missing key log nothing.
