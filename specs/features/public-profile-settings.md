# Feature: Username and profile privacy

Status: Agreed (Umair, via the M9A.3 brief; no teammate sign-off)
Owner: Umair
Related: `specs/features/settings-navigation.md`, `specs/features/activity-heatmap.md`,
`specs/features/streak.md`, `docs/rules/auth.md`

## Why

A learner may want to share their practice record on a CV or portfolio. Before any
public page exists, they need a stable address (a username) and an explicit choice
about whether anyone else can see their profile. Nothing is public unless its owner
says so. The profile page itself is a later milestone (M9A.4); this one only records
the choices and provides the narrow lookup that page will use.

## User stories

- As a learner, I want a unique username, so that my profile has an address.
- As a learner, I want to choose whether my profile is public, so that I decide what
  strangers can see.

## Acceptance criteria

- **AC1** — GIVEN a username THEN it is normalised (trimmed, compatibility forms
  folded, lowercased) and is 3–30 characters of lowercase letters, digits and single
  hyphens, starting and ending with a letter or digit. Otherwise the server returns a
  specific error (`too_short`, `too_long`, `invalid_chars`, `hyphen_edge`,
  `hyphen_double`).
- **AC2** — GIVEN a username that collides with a route, a system role or the
  product's name (`admin`, `settings`, `tracy`, ...) THEN it is rejected as `reserved`.
  Every top-level route under `src/app` is reserved, enforced by a test.
- **AC3** — GIVEN two learners claiming the same name in any letter case THEN exactly
  one succeeds and the other gets `taken`. The database's unique index decides, not a
  read followed by a write; names are stored normalised, so the index is
  case-insensitive.
- **AC4** — GIVEN every account, including all existing ones THEN its profile is
  `PRIVATE` with no username. Nothing becomes public by migration or by choosing a
  username.
- **AC5** — GIVEN a learner changes their username THEN their visibility is
  unchanged: private stays private and public stays public.
- **AC6** — GIVEN a learner turns the profile public THEN they must have a username
  (now, or in the same request); otherwise `username_required`. Going private is
  always allowed.
- **AC7** — GIVEN an update THEN it applies to the signed-in learner only. The request
  carries no user id (a strict schema rejects any key but `username` and
  `visibility`); signed out is `unauthenticated` and nothing is read or written.
- **AC8** — GIVEN the public lookup (`findPublicProfile`) THEN it returns an owner only
  when the username is valid and that profile is `PUBLIC`. A private profile, an unset
  one and a username nobody has give the same empty result, so private accounts
  cannot be discovered through it. It selects only the id (server-side) and username;
  never email, code, Tracy conversations or analytics.
- **AC9** — GIVEN Settings THEN a "Public profile" form has a username field, a
  "Make my profile public" checkbox (off by default), a plain explanation of what
  public will show and what is never shown, validation and availability errors,
  Save feedback, and controls disabled while saving. It says profile pages are not
  live yet.
- **AC10** — GIVEN the settings cannot be read THEN Settings says so and shows no form.

## Data / API

- `User.username String? @unique` and `User.profileVisibility ProfileVisibility
@default(PRIVATE)` (enum `PRIVATE | PUBLIC`, `prisma/schema/profile.prisma`). No new
  table, so no RLS migration; `users` already has RLS with no policy. The migration is
  generated by CI and adds a nullable column and a defaulted enum column (existing
  rows become `PRIVATE`).
- Server Action `updateProfileSettingsAction({ username?, visibility? })` returns
  `{ saved: true, username, visibility }` or `{ saved: false, error }`.
- Server-only: `getProfileSettings()`, `findPublicProfile(username)` and
  `toPublicProfileView()` (`src/server/profile/profile.ts`). The owner's `userId`
  returned by `findPublicProfile` must never reach a browser.
- No analytics events.

## Edge cases

- Two simultaneous claims: AC3. A unique violation on any other column is not
  reported as `taken`.
- A username cannot be cleared once set; the owner can make the profile private.
- Releasing a username (renaming) frees the old one for anyone immediately; there is
  no cooldown or redirect yet.
- The availability check is the save itself: there is no separate "is this free?"
  endpoint, so there is no extra way to probe which names exist.
- Before the migration runs the settings read is unavailable (AC10) and a save fails
  with a generic error rather than writing.
