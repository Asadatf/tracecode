I'd use Bricolage Grotesque for product headings, a highly readable sans-serif for dense interface text, and JetBrains Mono for code and variables. We should test the heading font at smaller sizes rather than applying it indiscriminately.
3. Component specifications
Component	Behavior
Problem statement	Readable description, constraints, examples
Code editor	CodeMirror 6, dark theme, line numbers, Python highlighting
Run code	Executes actual Python using Pyodide
Test results	Clear passed, failed, error, or limit-exceeded states
Replay action	Opens the selected test's actual execution trace
Replay controls	Back, next, timeline seek, active source line
State inspector	Actual variables, arrays, pointers where derivable
Hint entry point	Progressive assistance grounded in available evidence

Suggested desktop layout: approximately 40% problem panel / 60% editor, adjustable later with a draggable divider. The editor should have generous vertical space, and results should occupy a resizable lower panel rather than pushing the editor out of view.

On narrower screens, prioritize the editor and use tabs for Problem, Code, and Results.
4. The learner's interaction flow
1
Write — Learner edits Python in CodeMirror.

2
Run — Pyodide executes the submitted code in a Web Worker.

3
Inspect — The interface displays actual test results.

4
Replay — The learner opens a failed test's real execution trace.

5
Understand and fix — Relevant execution states and optional hints guide the next attempt.


We should keep the problem workspace and execution replay as separate, connected views initially. This preserves space for learning and matches the existing TraceCode direction. We can explore an inline debugger later if testing suggests that switching views interrupts learning.
5. Implementation architecture
CodeMirror 6

Learner writes Python


Web Worker + Pyodide

Actual execution, tests, bounded tracing


Trace contract

Source line, variable state, execution events


Replay visualization

Code highlight, arrays, timeline, explanations


A critical requirement: the UI must never display a predefined trace as if it came from the learner's code. The real trace contract remains the source of truth. If the tracer cannot confidently determine a pointer or event, the interface should omit it rather than inventing it.

Pyodide in a worker is appropriate for the initial MVP, with explicit timeout and trace-size controls. It isn't a hardened security boundary for arbitrary hostile Python.
6. What I'd deliberately leave out of screen one
No elaborate marketing animations, no unnecessary dashboard charts, no complex gamification, and no permanent AI chat sidebar taking up editor space. The optional tutor can open contextually when needed.

The priority is a truly polished Two Sum → Run → Inspect Failure → Replay → Fix experience.

This is the visual and interaction specification I'd use for our first iteration. It keeps the distinctive aesthetic encouraged by the 8x workshop while ensuring that every significant design decision supports TraceCode's learning philosophy.
