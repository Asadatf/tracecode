# Practice page design audit (read-only, no changes made)

Scope: [practice-workspace.tsx](src/components/trace/practice-workspace.tsx), [practice.module.css](src/components/trace/practice.module.css), [code-editor.tsx](src/components/trace/code-editor.tsx) and [page.tsx](src/app/[locale]/practice/[slug]/page.tsx). I read the code only. I didn't look at the rendered page.

## What works well
- **Layout:** The problem sits on the left and the editor and results on the right. The editor is dark, which sets it apart from the light panels.
- **Stage tracker:** Write, Run, Explore and Improve gives the learner a clear next step.
- **Run feedback:** The editor header shows a status label while the code is running or the runtime is loading.
- **Replay layout:** The replay panels keep a fixed height, so the page doesn't jump as steps advance.
- **Spacing:** Spacing is consistent, using `clamp()` for the page gutters.

## High priority
1. **The page ignores the app's shared header and theme.**
   - Practice renders its own hand-built header with a `⌁` logo, a problem select and a Progress link ([practice-workspace.tsx:355](src/components/trace/practice-workspace.tsx:355)).
   - The rest of the app now uses `ApplicationHeader` and `AccountMenu`, which are new and uncommitted.
   - So practice has no account menu and no settings link, and the nav looks different from the other pages.
   - It also loads its own fonts and defines its own colour variables, rather than using the global design tokens. `docs/rules/code-style.md` calls for design tokens.
2. **Almost every colour is a hard-coded hex value.**
   - Only about 8 `--` variables exist. Dozens of one-off greens, greys and reds are written inline (`#68746e`, `#758079`, `#8a9690` and so on). Several are near-duplicates.
   - There is no dark mode, and the page has a fixed light background.
3. **Contrast problems on the light panels.**
   - `.foot` (#8a9690), `.empty` (#8a9690), `.resultSummary` (#89958d) and `.index` (#83918a) on white or `#f4f5f2` are roughly 2.8–3:1. That fails the 4.5:1 WCAG AA minimum for small text.
   - Text is 10–12px in many places: `.testDetail` is 11px, `.example small` is 10px, `.coachHintLabel` is 10px and `.mutedDark` is 11px. Combined with the low contrast, this is hard to read.
   - The green `.btnRun` (#40be91 with dark text) is fine. The `.dot` green (#39a67e) on white is only about 3:1, though it is decorative.
4. **The editor is not strong for accessibility.**
   - The textarea has `color: transparent` over a separate highlighted overlay. If the two ever drift out of alignment, the user sees ghost text.
   - Windows High Contrast and forced-colors modes will likely show nothing in the editor.
   - Tab is trapped to insert spaces, with no documented escape. That is a keyboard trap.
   - I found no `:focus-visible` styles anywhere in the CSS. Buttons, the select and the textarea rely on browser defaults, and the editor sets `outline: 0`, so it has no focus indicator at all.

## Medium priority
5. **Inline styles and magic values leak into the TSX.**
   - Examples are `style={{ background: '#fff' }}`, `style={{ marginBottom: 12 }}` and `style={{ color: '#a74332' }}`, repeated three times for errors ([practice-workspace.tsx:681](src/components/trace/practice-workspace.tsx:681)).
   - The error colour `#a74332` differs from the declared `--red: #b44837`, which is never used.
6. **Status is shown by colour and a glyph only.** The pass and fail rows use ✓ and × plus a green or red pill. The text "Passed" and "Failed" is there, so this is acceptable. The glyphs sit in plain text with no label, which is minor.
7. **Emoji and unicode glyphs are used as icons.** These are `⌁`, `◫`, `▶` and `🔒` in the problem select. They render differently across platforms. `docs/rules/icons.md` says every icon must come from `@/components/ui/icons`.
8. **Responsive behaviour is thin.**
   - Only three breakpoints are used, and the main layout collapses at 900px.
   - `.workspace` has a `minmax(400px, …)` column, so between about 900 and 1000px the layout is tight.
   - The editor has a fixed height of 340px. The header row (brand, select, link) wraps rather than adapting.
   - `.progressGrid` stays at 3 columns on phones, and the attempts rows put two buttons next to the text, which will be cramped.
9. **Hierarchy competes in the page head.** The H1, the subtitle and the 4-chip stage tracker all sit in one row. The subtitle, "A small problem. A powerful way to understand your code.", is the same copy for every problem. It takes up space without helping the learner.
10. **The results panel is below the editor and starts nearly empty.** After Run, the learner has to scroll to see results on shorter screens. There is no auto-scroll or focus move to results. A status change is also not announced, because I found no `aria-live` region for run status, results or notices.
11. **Feedback sits in a different place on each run.** `.warn` notices appear below the whole workspace grid, far from the Run button. A user who hits "Write some code before running" may never see it.

## Low priority
12. **Dead or unused CSS.** `.btnDark`, `.btnGhost`, `.mono`, the `.custom*` block (for a custom-input feature that has no UI here) and `.mutedDark` partly overlap. A header comment still describes a port of an HTML prototype.
13. **A gap in the shadow system.** The panel shadow (`0.025` alpha) is barely visible, while the editor shadow is heavy. The result is flat panels next to a floating editor.
14. **The file is large.** `practice.module.css` is 922 lines and mixes practice, replay and teaching styles. `practice-workspace.tsx` is 753 lines. `docs/rules/code-quality.md` forbids god files.
15. **No loading skeleton for the route.** `progress/loading.tsx` exists, but I found no equivalent for `practice/[slug]`.
16. **Copy and label issues.**
    - "Run code" runs tests, and the results panel says "Test results", so the label could be "Run tests".
    - The footer says "First-load internet access is required for the Pyodide runtime…" in 11px light grey, although it is a real requirement.

## Suggested order
1. Switch to `ApplicationHeader` and the global tokens (items 1 and 2).
2. Fix focus styles and contrast, and add `aria-live` for run status and results (items 3, 4 and 10).
3. Replace the glyphs with the shared icons, and remove the inline styles (items 5 and 7).
4. Split the CSS and clean out the dead rules (items 12 and 14).

# Progress page design audit (read-only, no changes made)

I read these files and didn't look at the rendered page:
- [page.tsx](src/app/[locale]/progress/page.tsx)
- [loading.tsx](src/app/[locale]/progress/loading.tsx)
- [progress-sections.tsx](src/components/progress/progress-sections.tsx)
- [recommendation-card.tsx](src/components/progress/recommendation-card.tsx)
- [recommendation-insight.tsx](src/components/progress/recommendation-insight.tsx)
- [reminder-preferences.tsx](src/components/progress/reminder-preferences.tsx)
- [progress-empty.tsx](src/components/progress/progress-empty.tsx)
- [site-header.tsx](src/components/site-header.tsx)

## What works well
- **Design tokens:** The page uses `text-text-muted`, `bg-surface`, `border-border` and `text-success` throughout, so it follows the project's design-token rule. It is far cleaner than the practice page.
- **Shared components:** It uses `Button`, `Badge` and the shared icons from `@/components/ui/icons`.
- **Accessibility basics:**
  - Sections use `aria-labelledby`.
  - Tables use `scope="col"` and an sr-only label for the action column.
  - The summary is a `<dl>`.
  - Status messages use `role="status"`.
  - The loading skeleton is labelled.
- **Locale-aware links and times:** Links come from `@/i18n/routing`, and times go through `LocalTime`.
- **Wide tables:** They scroll inside their container instead of breaking the page.

## High priority
1. **The loading skeleton and the page use different shells.**
   - `loading.tsx` wraps its content in `application.module.css`'s `styles.page` with `max-w-6xl`. That file is new and uncommitted.
   - `page.tsx` still renders `SiteHeader` with `max-w-5xl`, which is a different container.
   - When loading finishes, the page will shift in width and gain a header the skeleton didn't show.
   - The skeleton also has no header area, and its layout (a 4-card grid, then a tall block) doesn't match the real page. The real page has a 3-item summary list, a table, and a two-column row.
   - This looks like a half-finished move to `ApplicationHeader`. Practice, settings and the home page appear to be in the same state.
2. **Sign out is hard-coded and misplaced.**
   - "Sign out" and "Sign in" are plain English strings in [page.tsx:80](src/app/[locale]/progress/page.tsx:80), while every other string goes through `getTranslations`. They will stay in English in other locales.
   - Sign-out sits beside the page title, which is an unusual place. The new `AccountMenu` and settings route are probably meant to own it.
   - The `!progress.authenticated` branch can't normally render, because the page already redirects anonymous users. That makes the signed-out `ProgressEmpty` component and the "Sign in" link effectively dead code.
3. **There is no visual hierarchy for the summary.**
   - The stats are bare `<dl>` text in a row, with no card, border or icon. They sit between the H1 and the large table and are easy to skim past.
   - There is no progress bar or ring for "solved N of total". It is plain text.
   - The recommendation card is a boxed panel above it and looks heavier than the numbers that matter.
4. **The page order buries the main content.** The order is recommendation, summary, problems table, recent runs and topics, then reminder preferences. Preferences are a settings concern. The new `/settings` route already has the same control, so this is a duplicate placed at the bottom of a progress page.
5. **The duplicated component can drift.**
   - [reminder-preferences.tsx](src/components/progress/reminder-preferences.tsx) and the new `src/components/notifications/reminder-preferences.tsx` are near copies. The newer one adds a cadence option, a `saving` label, TanStack Query and `captureClientError`.
   - Progress still ships the older one, so it has fewer options than settings and different error handling.

## Medium priority
6. **Table density.**
   - The problems table has six columns and a `min-w-[40rem]`, so it scrolls sideways on phones. The status column is the thing a learner scans for, and it is plain coloured text.
   - Status is colour plus a text label, so it is accessible, but it has no icon or badge. The `Badge` component is already used on the recommendation card and would be consistent.
   - The "Best" column shows "3/5 passed"-style text in mono, so it is hard to compare at a glance. A mini bar would read faster.
7. **Small text and muted colour.** Table cells use `text-sm`, the helper notes use `text-xs`, and many labels use `text-text-muted`. I can't check contrast without the token values. I'd verify `text-text-muted` on `bg-surface` and `bg-surface-subtle` is at least 4.5:1.
8. **Inconsistent corner radius and padding.** The cards use `rounded-sm` with `p-6`, the skeleton uses `rounded-lg`, and the empty-state CTA uses `px-4.5`. The skeleton and the real content don't match.
9. **The recommendation card holds a lot.** It stacks the problem, a reason, difficulty, focus concepts, an AI or fallback insight, the disclaimer, a refresh button and status text. That makes it long. The disclaimer is `text-xs` muted and sits between the insight and the button. It is easy to miss, and it is the honesty note.
10. **The refresh button gives limited feedback.**
    - `role="status"` is set on the message, but the message is only rendered after the action finishes.
    - The pending state swaps the label and shows a spinner icon. The spinner has no accessible label, and I don't see a `motion-reduce` guard (not verified).
    - "Cooldown" and "up to date" messages are shown in the same muted colour as the helper text, so they read as secondary.
11. **Reminder checkboxes.**
    - They use native inputs with `accent-accent` and `size-4`, which is small for touch.
    - The row label is clickable, so the target is larger than the box.
    - Saving is not announced until it completes, and saved and failed use the same small muted text.

## Low priority
12. **Empty states are weak.** "No recent runs" is a plain muted line with no call to action. A new user with no attempts sees a table of "Start" links but no explanation of how the page will fill in.
13. **The topics table is thin.** It is a two-column "solved/total" table that is easy to turn into a chart.
14. **The recent runs table has no problem link.** The problem name is plain text, not a link back to the problem. The problems table does have an action link, though.
15. **Typography.** Headings are `text-3xl`, `text-lg` and `text-base`, with `font-bold` on all of them. With the summary numbers also `font-bold`, there is little weight contrast.
16. **The max width of 5xl feels narrow beside the 1560px practice layout.** The two pages have different content widths.

## Cross-page consistency (practice vs progress)
- Practice uses its own header, fonts and ~40 hard-coded hex colours. Progress uses tokens and `SiteHeader`. Both differ from the new `ApplicationHeader` and account menu.
- Progress is on the token system and practice isn't, so a learner moving between them sees different greens, radii (`15px` against `rounded-sm`), button styles and type.
- The new application shell looks like the intended common layer. Moving both pages onto it would fix the largest inconsistencies at once.

## Suggested order
1. Pick the shell (`ApplicationHeader`) and make `page.tsx` and `loading.tsx` use it, with a skeleton that matches the real layout (items 1 and 8).
2. Move sign-out into the account menu, translate the leftover strings, and remove the dead signed-out branch (item 2).
3. Remove the progress copy of reminder preferences and link to `/settings` instead (items 4 and 5).
4. Give the summary and status real visual weight with cards, badges and progress bars (items 3 and 6).

# Landing page audit (read-only, no changes made)

I read the code and haven't seen the rendered page. The files were [page.tsx](src/app/[locale]/page.tsx), [landing-header.tsx](src/components/home/landing-header.tsx), [landing-sections.tsx](src/components/home/landing-sections.tsx), [problem-table.tsx](src/components/home/problem-table.tsx), [execution-tour.tsx](src/components/home/execution-tour.tsx), the cursor and scroll-reveal components, and the three CSS modules.

## What works well
- **Clear structure:** The page runs hero, interactive tour, narrative, 4-step loop, problem catalogue and closing CTA. Each section has an `aria-labelledby` heading.
- **Honest preview:** The tour is labelled "illustrative". It is built from a real fixture trace rather than a mock screenshot.
- **Reduced-motion support:** `ScrollReveal`, the cursor and the CSS all honour `prefers-reduced-motion`.
- **Focus styling:** There is a global `.page :is(a, button):focus-visible` ring (3px accent). That is better than the practice page.
- **Contrast tokens:** `--text-muted` is #4d5852, which is dark enough on the light surfaces, so the landing page has fewer contrast problems than practice.
- **Responsive breakpoints:** There are breakpoints at 1120, 780, 640 and 540px, and the hero collapses to a single column.
- **Locked rows:** Signed-out users see a lock icon, a "Locked" or "Free" note and a link that goes through login and returns.

## High priority
1. **The landing page ships a custom cursor, and it hides the real one.**
   - `landing-cursor.module.css:44` sets `cursor: none !important` on the page whenever a fine pointer is detected.
   - The custom cursor is a 28px outlined white arrow drawn by JS. Its position lags a frame behind and it is hidden over text, so users lose the native cursor in some places and see their own in others.
   - It is purely decorative, and it works against usability. This is the single biggest risk on the page.
   - It also adds a `pointermove` and `scroll` listener doing `elementFromPoint` work on every frame.
2. **Two token systems fight each other.**
   - `globals.css` defines `--landing-bg: #0f1412` (dark) and `--landing-accent`. `landing.module.css` redefines `--bg`, `--text` and `--accent` locally as a light theme. The page background is then built from `--landing-bg`, which is the dark colour.
   - The `.page` rule even carries a comment about keeping "automatic dark tokens available". The result is a mix of dark base, light overrides and `color-mix` tints. Whichever theme wins, it is hard to reason about and easy to break.
   - There are about 35 raw hex values in `landing.module.css` on top of this.
5. **Three headers exist and they have diverged.**
   - `LandingHeader` has its own account `<details>` menu, its own sign-out and its own initials logic.
   - The new `ApplicationHeader` and `AccountMenu` (uncommitted) do the same job with different markup, an extra visible Sign out button and a Settings link. `SiteHeader` still exists too.
   - The landing menu has no Settings link, and the account initial uses the first letter of the email only. The new `account-initials.ts` is not used here.
   - The landing header has no `aria-current`, so the current section is not indicated.

## Medium priority
4. **Dead code.** `landing-motion.tsx` (`LandingMotion`) is not imported anywhere. It is a 134-line WAAPI reveal system that duplicates `ScrollReveal`, and it queries `styles.*` classes. Two reveal systems in the repo (CSS-driven `data-reveal` and this one) will confuse the next editor. It is also an untracked file.
5. **Reveal-on-scroll can hide content.**
   - Sections start in `data-state="pending"` and only show when the `IntersectionObserver` fires. Content is hidden until JS runs, so it is invisible without JavaScript or if the observer fails.
   - The `-12%` root margin means short viewports or fast jumps to `#problems` may leave sections pending. Focus is handled (the `focusin` handler reveals), but anchor jumps (`#how-it-works`, `#problems`, `#narrative-title`) rely on the observer.
   - Printing and screenshot tools will also show blank sections.
6. **Hero density.** The hero carries an eyebrow, a title, a description, three CTAs (primary, secondary and a text link), a trust line and the whole interactive tour. Three calls to action compete. The text link "See all problems ↓" and the secondary "Explore the demo" overlap in purpose.
7. **The tour is a lot to ask above the fold.**
   - `grid-template-columns: minmax(300px, .76fr) minmax(620px, 1.24fr)` needs at least about 920px plus the gap, so the two-column layout only works from roughly 1000px.
   - Between 1000 and 1120px the tour is cramped. Below 1120px it stacks, so on tablets the hero is very tall.
   - The tour's four stage buttons use `aria-pressed`, which suits toggles. A stepper would suit tabs or a step list better. The code lines are `div`s with a `code` child and the line numbers are not hidden from screen readers, so the source reads out "1 def… 2 …".
8. **Many text sizes are small.** Tour labels, table headers, kickers (12px, uppercase, wide letter-spacing) and the "illustrative" note are small and heavy-tracked, which hurts legibility.
9. **`overflow: clip` on the page root** hides anything that spills out. The hero's decorative ring (`right: -8%`) relies on it. It is also why a horizontal scrollbar doesn't appear, so any real overflow bug would be masked.

## Low priority
10. **The problem table has few columns of real value.** On narrow screens a five-column table (number, title, topics, difficulty, status) either scrolls or gets cramped. I didn't see a mobile card layout. The empty state is a single cell.
11. **Heavy motion CSS.** `landing-motion.module.css` is 322 lines and adds per-row catalogue animations on top of the reveal system. Hover lifts (`translateY(-1px)` plus shadow) on every CTA are fine, but combined with entry animations, cursor effects and a decorative ring the page is busy.
12. **Hard-coded English in the tour.** `execution-tour.tsx` hard-codes `two_sum.py` and the code. That's fine for a demo. The header brand "tracecode" and the ⌁ glyph logo are plain text and unicode rather than a logo asset or icon.
13. **A very large stylesheet.** `landing.module.css` is 1,683 lines and `landing-motion.module.css` another 322. They are both well above the "no god files" guidance.
14. **Link semantics.** The hero's secondary and text CTAs are `<a href="#…">` rather than `Link`, so they skip locale-aware routing. That works for in-page anchors. The header nav does the same, so from a non-home page these would break if the header were reused. The new `ApplicationHeader` uses `/#problems` for that reason.
15. **No `loading.tsx` for `/`.** The page does a progress query before first paint, so signed-in users wait on that.

## Cross-page picture
| | Practice | Progress | Landing |
|---|---|---|---|
| Header | own hand-built | `SiteHeader` | `LandingHeader` |
| Colours | ~40 hex values | design tokens | mixed tokens and ~35 hex values |
| Theme | fixed light | tokens (auto dark) | light override on a dark token base |
| Account menu | none | none (sign-out button in the page) | own copy |
| Cursor/motion | none | none | custom cursor, 2 reveal systems |

The four header implementations (including the new `ApplicationHeader`) are the clearest sign that the pages need one shell. The landing page also has the most self-contained design effort, so it is the one most worth keeping as the visual reference.

## Suggested order
1. Remove or drastically limit the custom cursor (item 1).
2. Decide which header is canonical, probably `ApplicationHeader` with `variant="home"`, and delete the others (item 3 and the cross-page table).
3. Clean up the tokens so the page has one light theme (item 2), and remove `landing-motion.tsx` (item 4).
4. Make reveal-on-scroll degrade safely (item 5) and trim the hero CTAs (item 6).

Tell me which of these you want to act on.
