# TraceCode — M8: Context-Aware AI Tutor

## Project Context

We are implementing **M8: Context-Aware AI Tutor** on the branch:

`feat/m8-contextual-ai-tutor`

The dashboard work has already been merged into `main`.

TraceCode is a coding education platform built around actual Python execution, test grading, execution replay, progressive hints, learning analytics, and evidence-based recommendations.

M8 introduces a real AI Tutor that understands what a learner is doing and helps them reason through problems, mistakes, execution behavior, and algorithmic concepts.

The Tutor must function as a **pedagogical assistant**, not a generic code-generation chatbot.

### Core decisions

- Initial AI provider: **OpenAI**
- Initial model: **gpt-4o-mini**
- Architecture: **Provider-independent AI adapter**
- Future provider support: **OpenRouter**
- Knowledge retrieval: **Structured, deterministic retrieval**
- Embeddings/vector databases: **Not required**
- Conversation storage: **Browser sessionStorage**
- Conversation isolation: **Per authenticated user and problem**
- Conversation limit: **15 learner questions per chat**
- Refresh behavior: **Preserve conversations**
- Logout behavior: **Clear conversations**
- Database persistence for tutor chat: **Not required**
- Existing M7 AI functionality: **Must remain operational**

M8 must be completed without introducing unrelated features or redesigning the existing Practice Workspace.

# Phase 3 — Context-Aware Tutoring

The Tutor must understand the learner's active coding environment.

## Context sources

Use relevant, available evidence from:

### Current problem
- Problem ID and title.
- Problem description.
- Difficulty.
- Concepts and topics.
- Constraints.
- Examples.
- Expected function contract.

### Current learner code
- Current Python editor contents.
- Relevant source lines.
- Current unsaved changes, when intentionally submitted.

### Execution and grading
- Latest execution outcome.
- Passed and failed test cases.
- Relevant expected versus actual outputs.
- Runtime errors and syntax errors.
- Existing execution diagnostics.

### Execution replay
- Selected replay step.
- Current source line.
- Available variable states.
- Relevant preceding execution events when required.

### Learning context
- Existing hint level.
- Relevant recent attempts.
- Previously demonstrated misconceptions, only when supported by evidence.
- Existing M7 evidence and recommendations where appropriate.

Do not load unnecessary historical data.

## Evidence-grounding requirements

The Tutor must distinguish between:

1. **Observed evidence:** Actual execution records and test results.
2. **Reasoned interpretation:** An explanation inferred from observed behavior.
3. **General programming knowledge:** Facts about Python, algorithms, and data structures.

Never fabricate:

- Test results.
- Variable values.
- Execution traces.
- Source line numbers.
- Failed inputs.
- Runtime measurements.
- Previous learner actions.

If execution evidence is missing or truncated, acknowledge the limitation.

Do not claim to have executed code through the AI provider.

## Privacy boundary

Opening the AI Tutor panel must NOT automatically send the learner's code to OpenAI.

Only transmit relevant code and execution context when the learner deliberately submits a tutoring request.

The client should clearly communicate that AI tutoring uses relevant problem and code context.

# Phase 5 — Pedagogical Tutoring Behavior

The Tutor's purpose is to improve learner understanding.

It should:

1. Prefer guided questions and Socratic explanations.
2. Help learners identify mistakes independently.
3. Use actual failing test cases when available.
4. Explain execution flow and variable changes.
5. Explain why an algorithm works or fails.
6. Help learners understand relevant Python concepts.
7. Provide progressively stronger hints.
8. Explain time and space complexity accurately.
9. Discuss optimization only when supported by evidence.
10. Encourage learners to revisit their own reasoning.

## Progressive solution disclosure

Do not immediately reveal complete solutions.

Use an escalation strategy:

**Level 1 — Conceptual guidance**
Help learners identify the relevant concept or misunderstanding.

**Level 2 — Strategic hint**
Suggest an approach without giving full implementation details.

**Level 3 — Targeted implementation guidance**
Discuss a particular part of the learner's code or algorithm.

**Level 4 — Explicit full-solution request**
Only provide a complete worked solution when the learner explicitly requests it and the tutoring policy permits it.

When displaying a worked solution, include an explanation of why it works.

Keep the disclosure policy consistent across problems.

Avoid unnecessarily repeating previously provided hints.

## Example interactions

A learner using nested loops for Two Sum might ask:

"Why is my solution slow?"

The Tutor should explain the relevant complexity using their implementation and available evidence, rather than immediately replacing the code.

A learner inspecting a Valid Parentheses replay might ask:

"Why did this condition fail?"

The Tutor should use the selected execution state when available.

For syntax errors, explain the actual parser error without inventing a runtime trace.

# Phase 6 — Session-Based Conversation Management

The Tutor must support conversational continuity.

**Browser refresh must not erase the conversation.**

Conversation history should remain available within the current browser-tab session until reset, logout, or session termination.

## Storage

Use browser `sessionStorage`.

Do not create database tables or persistent server-side chat storage for M8.

Store only:

- Conversation ID.
- Authenticated user identifier for namespace isolation.
- Problem ID.
- Learner messages.
- Assistant responses.
- Essential timestamps.
- Successful question count.
- Minimal required conversation metadata.

Never store:

- API keys.
- Full execution traces.
- Large grading payloads.
- Provider credentials.
- Unnecessary personal data.
- Raw provider diagnostics.

Validate stored conversation data before restoring it.

Use a bounded storage size and handle storage failures gracefully.

## Conversation isolation

Each authenticated learner and each problem must have an independent conversation namespace.

Expected behavior:

| User action | Required behavior |
|---|---|
| Minimize Tutor | Preserve conversation |
| Expand Tutor | Preserve conversation |
| Resize panels | Preserve conversation |
| Close and reopen Tutor | Restore conversation |
| Switch Write/Run/Explore/Improve | Preserve conversation |
| Refresh browser | Restore conversation |
| Navigate to another page and return | Restore conversation |
| Switch to a different problem | Load that problem's conversation |
| Return to previous problem | Restore its conversation |
| Log out | Clear the user's locally stored Tutor conversations |
| Log in again | Begin fresh conversations |
| Close browser tab | Session may end |

The Tutor component must not lose its conversation merely because its UI panel is conditionally unmounted.

Place state management at a stable architectural level, or reliably hydrate it from sessionStorage.

## Logout behavior

Integrate cleanup with the existing authentication/logout flow.

Clear only the relevant TraceCode Tutor session entries.

Ensure conversations from one authenticated account cannot be displayed to another account using the same browser tab.

Do not globally clear unrelated browser storage.

# Phase 7 — Fifteen-Question Conversation Limit

Each Tutor conversation allows a maximum of **15 successful learner questions**.

An AI response does not count toward this limit.

## UI requirements

Display a compact usage indicator, such as:

`6 / 15 questions used`

or:

`9 questions remaining`

Do not make this indicator visually distracting.

## Limit behavior

- Allow up to 15 learner questions per conversation.
- Count a question only after a successful assistant response is committed to the conversation.
- Prevent duplicate sends while a request is pending.
- Prevent concurrent requests from bypassing the client-side question limit.
- At 15 questions, make the conversation read-only.
- Preserve the entire existing conversation for reading.
- Show a clear "Start new chat" action.
- Starting a new chat resets the 15-question allowance.
- A new chat should not carry over the previous conversation's transcript.
- New chat must retain the current problem context.

The 15-question limit is a **conversation-length limit**, not a daily usage allowance.

Learners may create new conversations.

## Failed requests

Do not consume a question for:

- Network failures.
- Provider timeouts.
- Rejected API requests.
- Server errors.
- Authentication failures.
- Requests that produce no successful assistant response.

Allow retrying failed messages without duplicating learner questions.

## Security distinction

Because sessionStorage is client-controlled, the 15-question limit must not be treated as a security or billing control.

Maintain independent server-side:

- Request throttling.
- Authentication checks.
- Payload-size limits.
- Output-token limits.
- Abuse prevention.

Do not build a database-backed quota engine merely to enforce the 15-question UX limit.

## Server-side throttling on Vercel — assessment

**Current design:** `src/server/tutor/rate-limit.ts` is a per-instance in-memory token bucket (20 req/min per userId, 60 s rolling window).

**Vercel-specific limitations, honestly:**

1. **Multi-instance:** Each warm serverless function has its own `Map<string, Bucket>`. A user bouncing between instances could in principle see the bucket reset. In practice, Vercel's affinity for a warm user is reasonably sticky, and the call cost is dominated by GPT-4o-mini output (~600 tokens max = fractional cents per call), so even a 3× multiplier from instance scatter stays bounded.
2. **Cold starts:** A cold invocation starts with an empty bucket — same effect as point 1.
3. **No cross-user burst control:** The limit is per userId only; there is no global ceiling. If 1 000 authenticated learners each sent 20 req/min, that's 20 000 req/min to OpenAI. OpenAI's own account-level rate limit (TPM/RPM for `gpt-4o-mini`) is the final backstop here.

**Mitigations that are already present and do the real work:**

- The tutor is **authenticated**: anon traffic gets 401 at the route edge before any provider call.
- **Payload is bounded** (code ≤ 8 KB, messages ≤ 20 × 2 KB, 3 failed tests, hard timeout 20 s, output ≤ 600 tokens).
- **Cost per call is small** — the 15-question UX cap and these bounds together make a single learner's worst-day cost a known, small number.
- **`ai_usage` captures every call** with feature=`tutor_chat`, enabling the spend dashboard to detect abuse retrospectively.

**Not adding** Redis/Upstash/KV. The specs explicitly say "Do not introduce Redis or a new infrastructure service solely for this milestone unless clearly necessary". The current setup is "reasonable server-side throttling", matches the spec, and the costs stay bounded by the other controls above. If a future sustained-abuse incident materializes, the smallest upgrade is Upstash Ratelimit at the route edge — a one-file change.
