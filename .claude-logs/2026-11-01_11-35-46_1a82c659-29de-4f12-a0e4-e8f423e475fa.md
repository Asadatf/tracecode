**Metrics and how they're calculated**
- **Totals:** attempts, passed (`allPassed`), failed, and pass rate = passed ÷ attempts. Pass rate is `null` when there are no attempts.
- **Solved problems:** problems attempted and solved. For each problem, the number of attempts it took to first pass all tests, plus the mean and median across solved problems.
- **Ordering:** attempts are sorted by `createdAt`, with ties broken by `id`.
- **Per-problem history:** every submission, with a pass fraction = tests passed ÷ tests total (`null` if there were no tests). Also the first, latest and best fraction, and the change from first to latest.
  - The trend is `improving`, `declining` or `flat`. It is `single_attempt` when there are fewer than two attempts with tests.
  - A count of attempts that scored better than the one before.
- **Replay engagement** = linked replay sessions + fallback events. A linked replay writes both a session and an event, so for each (problem, test) only the events beyond the session count are counted as fallbacks, with a floor of 0. Nothing is counted twice.
- **Hints:** a reveal recorded as `…:L1`, `:L2` or `:L3` counts as Observation, Reasoning or Strategy. Anything else counts as `unclassified`. There is also a distinct count, where revealing the same hint on the same problem again counts once.
- **Repeat failures:** a run of 2 or more failed attempts in a row on one problem. A recovery is such a run followed directly by a pass. The longest failure run is also reported.
- **No activity:** `hasActivity: false`, every count is 0, and every rate, mean and median is `null`, never NaN. A problem with only replay or hint activity is listed but not counted as attempted.
- **No causal claims:** hints and replays are counted next to outcomes; nothing says one caused the other.

**Data limitations**
- Learning events don't store an attempt id, so replay de-duplication matches by count per (problem, test), not by exact pairing. All replays recorded before M4's linking fix show up as fallbacks.
- Pass/fail comes from the learner's browser and isn't verified by the server (ADR-0001).
- Stats are recounted from the `attempts` rows, not taken from the `ProblemProgress.attempts` counter.
- There are no timestamps on hints relative to attempts in the output yet. Hint events do have `createdAt`, so this can be added if M7 needs it.

## Replay check
In the client, `persistReplay` calls one of two actions:
- **Linked replay** (the attempt has a database id): it calls `recordReplaySession`, which writes **both** a `replay_sessions` row and a `replay_inspected` event, one after the other and not in one transaction.
- **Fallback replay** (no database id): it calls `recordLearningEvent`, which writes the event only.

So a linked replay = 1 session + 1 event, which is what M6.1 assumes.

For the regression test, I moved the replay row payloads into [replay-writes.ts](src/lib/learning/replay-writes.ts). `recordReplaySession` and the `persistReplay` fallback now build their writes from it; the rows written are unchanged. [replay-writes.test.mts](src/lib/learning/replay-writes.test.mts) feeds those exact payloads into the statistics and confirms each replay is counted once, for linked-only and for mixed linked and fallback replays.

## M6.2 behavioural analysis
[behavior.ts](src/lib/learning/behavior.ts) holds `analyzeLearningBehavior(statistics, records)`. It reuses M6.1's ordered history, first-solve index and failure-run counts instead of recalculating them. `getLearningAnalytics()` (which replaces `getLearningStatistics()`) loads the records once and returns `{ statistics, behavior }`.

**Observed facts:**
1. **Repeated failures:** each problem gets one pattern: `no_attempts`, `no_failures`, `isolated_failures`, `repeat_failures_recovered` or `repeat_failures_unresolved`. Also reported:
   - Tests that failed in 2 or more attempts, with their longest run of consecutive failures and whether the latest attempt still fails them.
   - How many failures the history currently ends on.
2. **Score changes:** across consecutive attempts that had tests: drops, unchanged steps, largest gain, largest drop, and failures after the first solve. Rises are M6.1's `stepImprovements` and aren't repeated.
3. **Hint reveals:**
   - Observation, Reasoning and Strategy counts split before and after the first solve; all count as before if the problem is unsolved.
   - Whether a Strategy hint came before the first solve.
   - For each prompt: levels revealed, highest level, skipped levels, and whether they were revealed in order.
   - Attempts submitted after the first reveal.
4. **Replay vs submissions:**
   - Linked replays on failed vs passed attempts.
   - The share of failed attempts that had a linked replay.
   - Replays before and after the first solve, timed from `replay_inspected` events since every replay writes one.
   - Attempts submitted after the first replay.
5. **Fail → pass:** for each pass that directly follows one or more failures: the failed attempt ids, the last failure's score, and the hints and replays recorded between the first failure and the pass. These are labelled `coOccurring`. The summary counts these transitions with a hint, with a replay, and with neither.

**Inferred signals:** these are hypotheses about understanding, not facts. Each is tagged `basis: 'inferred'` and carries the evidence behind it:
- `independent_first_solve`: no hint or replay before the first solve.
- `first_solve_after_strategy_reveal`.
- `possible_persistent_misconception`: the same test failed in 3 or more consecutive attempts.
- `unresolved_struggle`.
- `regression_after_solve`.

None of them, and no metric, says a hint or replay caused a pass.

**Timing rule:** an event counts as before an attempt only if its timestamp is strictly earlier; an event at the same instant counts as after.

## Limitations
- Learning events carry no attempt id, so fallback replays can't be tied to a specific attempt. Only linked sessions give the failed vs passed split.
- If a linked replay's event write fails, the session still counts in M6.1 totals but is missing from the M6.2 replay timing.
- Timing uses database timestamps, and attempt saves can land later than the replay. Ordering is accurate to the second, not proof of sequence.
- The 2-in-a-row and 3-in-a-row thresholds are fixed rules, not tuned.
- Pass/fail comes from the learner's browser and isn't verified by the server (ADR-0001).

## Suppression and minimum data
- **Score trends** need at least 3 measurable submissions on the problem. They appear only while the latest attempt still fails, and never alongside a regression, which already explains the change.
- **Recovery** isn't reported while a failure run is still open.
- **Persistent test failure** is reported only for a test that still fails, so it never contradicts a later pass.
- **First solves:** a problem gets either `independent_first_solve` or `first_solve`, never both.
- **Replays not used** needs at least 3 failed submissions.
- **Fewer than 3 submissions in total** adds a `limited_history` insight, and no trend is drawn from two data points.
