## 2. Your audit questions, answered

| Question | Finding |
|---|---|
| Calculation | Fully derived at request time from `attempts`. Nothing is stored. Distinct UTC days → current and longest run. Current is alive only if the last active day is today or yesterday (`streak.ts:62-70`). |
| What qualifies | Any saved attempt with `status === 'completed'`, meaning the code ran to the end. Syntax errors, timeouts and engine errors do not count. |
| Failed attempts | **Yes, they count.** Code that runs but fails tests still has status `completed`. This matches your intent. |
| Re-attempts on solved problems | **Yes, they count.** `saveAttempt` always inserts a row, and the streak ignores `ProblemProgress`. |
| Unchanged starter or trivial runs | **They count, which contradicts your intent.** `runTests()` only blocks `code.trim() === ''` (`practice-workspace.tsx:~464`). Starters are valid Python (for example `return -1`), so an unmodified starter returns `completed` and earns the day. Nothing compares the source to `problem.starter`. |
| Per-day dedup | A `Set` of UTC date strings, so a day counts once. The DB is not deduped: every run is a row. The query pulls every completed attempt in 730 days, not distinct days, on every page render (the flame is in `AppShell`). |
| Cross-session and cross-device | Yes. It is computed server-side from the DB keyed on the Supabase user id. Signed-out users get no streak, and no attempts are persisted for them (`isAuthenticated` gate). |
| Date boundary and timezone | UTC only, consistently. `utcDay` uses `toISOString`, and the Problems calendar and its countdown also use UTC. There is no per-user timezone. A learner in UTC-8 gets a day boundary at 4 pm local, and UTC+10 at 10 am. This is a real fairness and UX problem for a habit product. |
| Persisted or placeholder | The flame and calendar use real persisted data. The only placeholders are the dev-only "Streak at risk" sample notification in `src/lib/notifications/demo.ts` and a missing-DB fallback that shows a neutral flame with no numbers. |
| Calendar's source | `summary.activeDays`, the same array that feeds `computeStreak`. The UI and the stats cannot diverge. |

## 4. Bugs, architectural problems, missing pieces
1. **Trivial-run loophole.** An unchanged-starter run earns a streak day.
2. **Forgeable.** `saveAttempt` takes `status`, `allPassed` and `testsPassed` from the client as `z.string()` and numbers. `tests` is unchecked against the real test set. A single direct server-action call mints a streak day. This is acceptable for a private flame, but **not** for a public profile, a leaderboard or verified achievements (see the profile section below).
3. **Unbounded read on every page.** The streak query is full rows per attempt on each navigation. A daily-aggregate table would fix this.
4. **No per-user timezone.**
5. **Spec gap.** The spec is silent on challenge attempts and starter-code handling.
6. **Dev-only fake notifications.** `NotificationBell` merges three hardcoded samples outside production (`notification-bell.tsx:47`). This is harmless in production but misleading in demos.

## 8. Integrity feasibility
| Control | Reality |
|---|---|
| Restrict copy/paste | Trivially bypassable (dev tools, a second device). It works as friction only. It also harms accessibility and IME users. |
| Detect tab switch or blur | Feasible via `visibilitychange` and `blur`. It is only a signal. It is spoofable, and it false-positives on notifications and system dialogs. |
| Detect other apps or windows | **Not possible** in a browser. |
| Screenshot prevention | **Not possible.** Do not claim it. |
| Webcam | Permission is feasible, but continuous monitoring has a heavy privacy and GDPR cost, consent needs, and no reliable inference. It is not recommended. |
| Hidden tests plus server grading | The only real integrity control for correctness. |
| Overall | Everything client-side is deterrence, not prevention. Only server grading with hidden tests produces a trustworthy result. Even then, "someone else wrote it" or an AI solved it is undetectable. |

- **Public identity:** opt-in username only, linking to the profile.

# System 2 addendum: weekly leaderboard feasibility (read-only)

I changed nothing. I grepped the repo for `leaderboard`, `weekly`, `achievement`, `username` and week-start logic. The only hits are an unrelated `Badge` UI component, a comment in `app-error.ts`, and the weekday labels in `month-grid.ts`. So this part of the product has no code or schema yet. The feasibility conclusions below build on the earlier System 2 findings.

## 1. What exists and what doesn't

| Need | Status |
|---|---|
| Exam results as scoring source | **Missing.** There is no challenge or exam model. `Attempt` can't tell exam from practice (no kind, no date, no timer). |
| Public identity | **Missing.** `User` has only `id` and `email` (`prisma/schema/example.prisma:13`). There is no username and no visibility flag. |
| Week boundary | **Missing, and trivial.** All date logic is already UTC (`streak.ts`, `daily-problem.ts`). The week is `Date.UTC` of the date minus `(getUTCDay()+6)%7` days. The calendar grid assumes Sunday-first (`month-grid.ts:32`), so don't reuse it for week math. |
| Ranking, archive, achievements | **Missing.** |
| Trustworthy grading | **Missing.** The browser reports pass/fail, so every score is forgeable (ADR-0001). |
| Scheduler for weekly close | **Partial.** `vercel.json` has one daily cron at 15:00 UTC (`0 15 * * *`). That is the only slot, so a close at Monday 00:00 UTC can't run on time. |

## 2. Recommended model (minimum)

**Per-exam row.** `challenge_attempts`, with a unique key on `(userId, challengeDate)`:
- `startedAt` and `submittedAt`, both stamped by the server
- `testsPassed`, `testsTotal`, `finalCorrect`
- `scoreVersion`
- `verified` boolean (see below)
- `weekStart` (a Date column, derived)

**Weekly standing.** Compute from the daily rows rather than keep a live counter. Add `weekly_results` as a snapshot written once at close: `(weekStart, userId, rank, score, daysPlayed, tiebreakData)`. It is append-only and never deleted. This one table is the archive, the source for the public Top 20, and the source for profile achievements.

**Achievements.** `weekly_results` already holds them, so don't add a second table. A profile shows rows where `rank <= 20` and the user has opted in. This avoids duplicating data and keeps the display choice in profile settings.

## 3. Closing the week

- **Live board:** compute on read. At 20 players per page this is one grouped query over at most seven days of rows per week.
- **Archive:** a close job writes `weekly_results` once, idempotently. Use the existing pattern of a unique key and `ON CONFLICT DO NOTHING` (as in `learning_notifications`).
- **Timing:** Monday 00:00 UTC can't be hit by the existing cron. Two options:
  - **a)** Run the close from the existing 15:00 UTC cron, or lazily on the first read after the boundary. The live board is always correct because it derives from rows, and only the archive write is delayed.
  - **b)** Upgrade the plan for a precise cron.
- I recommend (a). The archive is just a snapshot of a deterministic query, so a late write loses nothing. The one rule: a late exam submission after Monday 00:00 UTC must never enter the closed week, so assign the week from `submittedAt`, not from write time.

## 4. Visibility rules

- **Public:** top 20, opted-in users only. Decide whether non-opted users are skipped or the list simply shows fewer rows. I recommend skipping them, so opting out doesn't leave a gap.
- **Private own rank:** returned only from a session-authenticated server read for the caller's own user id. Compute rank by counting users with a better score tuple in the same week. This is cheap and needs no stored rank.
- **A learner who didn't opt in** should still see their own rank privately, without being listed.
- **Rank among whom:** decide whether the private rank counts all participants or only the opted-in ones. I recommend all participants, labelled "of N players".
- **Privacy:** the public payload is username, rank, score and days played. It has no email, no source and no user id.

## 5. Scoring and fairness

**Don't let multiple submissions inflate scores.** The `(userId, challengeDate)` unique key means one scored result per day. Score by the first Submit, with extra Run presses recorded but never scored. A retry that replaces a worse result would reward brute-force guessing, so I advise against "best of N".

**Weekly score.** Sum of daily scores over Monday to Sunday, up to 7 days. Proposed daily score:
- primary: tests passed ÷ total (only a full pass earns full credit)
- then time taken, as a bounded bonus so speed can't outweigh correctness
- a missed day scores 0

**Transparent tie-breakers, in this order, published on the page:**
1. Higher weekly score
2. More days fully solved
3. Lower total time on solved days
4. Earlier time of the final scoring submission
5. Stable fallback (earliest account or user id), so ranks never flicker

**Fairness concerns:**
- **Time-zone fairness.** A fixed UTC release is early morning in some regions and midnight in others. A weekly sum dampens this, but it's a real participation factor.
- **Time bonus favours fast typists, not better engineers.** Cap it.
- **Missed days punish part-time learners.** A weekly total rewards volume. That conflicts with the habit-forming goal only if the weekly total is the only game, so keep the streak separate.
- **Fewer than 20 players** in early weeks. Show the board anyway and don't pad it.
- **Small catalogue.** Six problems mean repeats, and learners can memorise answers. This is a content problem, not a ranking problem, and it caps how fair the board can be.
- **Time taken:** compute from the server's `startedAt` to `submittedAt`. Never trust a client timer.
- **Definition of "start".** If the clock starts at page open, a user can open it, read the problem and walk away. If it starts at an explicit Begin click, the user can pre-read the problem elsewhere. This needs a product decision.

## 6. Cheating risks (and which are fixable)

| Risk | Fixable? |
|---|---|
| Forged result via a direct server-action call (`status`, `testsPassed` are client-supplied) | **Yes, only with server-side grading** against hidden tests. This is a hard requirement for any public ranking. |

| Replaying a request or racing two submissions | Yes, via the unique key and a transaction. |
| Clock manipulation | Yes, with server timestamps only. |
| Username abuse and impersonation | Moderation plus a reserved-names list. |

**Bottom line:** without server-authoritative grading, any public leaderboard ranks who can call the API most convincingly. I recommend gating the public Top 20 on server-graded results (`verified = true`), and showing unverified results only on the learner's private screen.

- Prisma `P2022`, with the column named in `meta.column`. That means `attempts.meaningful`, `"meaningful"` or `meaningful`.
- Raw-query `P2010`, where `meta.code` is `'42703'` and the message names the column.
- A bare driver error whose `code` is `'42703'` and whose message names the column.

If the column can't be identified (for example `(not available)`, or no `meta`), it does **not** fall back and the error propagates. `P2022` for any other column, `P2002`, `P1001`/`P1008`, `23503`, `42P01`, and plain `Error`s all propagate.

**Write path (`saveAttempt`).** `writeWithOptionalColumns` tries the write with `meaningful` and `codeFeatures`. If the database reports one of them undefined, it drops only that column and retries. It ends at the plain pre-M7 write. This works whichever column Postgres names first, and it never loops, because each retry removes one column. The old `codeFeatures` compatibility is kept and now follows the same strict rule.

**Read path (streak).** `readWithColumnFallback('meaningful', …)` switches to the legacy query only for that column.

## 3. Scheduling and retry policy
- **Enrol:** the first qualifying all-pass on a problem makes review 1 due the next UTC day.
- **Intervals:** review 2 is due 3 days after review 1 is completed, and review 3 is due 7 days after review 2. Completing review 3 ends the cycle. Days are UTC, and a late review counts from the day it was actually completed.
- **One pass, one stage:** a pass before the due day does nothing. The advance is one conditional update on the stage the caller saw, so duplicate or simultaneous requests move exactly one stage.
- **Retries:** an unsuccessful attempt changes nothing. The review stays due, with no reset and no penalty.
- **Trust gate:** a pass counts only if it's a completed run, the server judged it meaningful, and its results cover every catalogue test exactly once, all passed.

## 2. What M9B can reuse
- **Execution engine:** `RUN_PROGRAM`, the engine's Python half. It is stdlib-only (`json`, `copy`), reads a `REQUEST_JSON` global, and the repo already runs it under plain CPython in tests. It runs all tests in one process with no timeout of its own, and echoes `expected` and `actual` in results. `buildRunRequest` also handles the in-place (`mutate-arg`) grading mode.
- **Editor and statements:** `CodeEditor`, the statement/examples rendering, and the browser Pyodide `runCode` for a local Run on the public examples.
- **Streak and activity:** an exam submission is an `Attempt` for the existing streak and activity systems (decision below).
- **Public profile data:** `User.username` and `profileVisibility`, plus the public profile page.
- **Notification, flag and auth infrastructure:** the existing patterns, including the feature-flag registry, which can ship M9B dark.
- **Daily calendar:** `ProblemCalendar` is the entry point, and `problemForDate` is the starting assignment rule.
- **Schema conventions:** CI-generated create-table migrations followed by a hand-written RLS migration, per `docs/rules/migrations.md`.

**What does not exist:**
- **No safe server-side Python grading.** ADR-0001 explicitly rules out a server-side sandbox for practice.
- **No hidden tests.** All catalogue tests are in `PROBLEMS`, and the practice workspace imports that, so they ship to every browser.
- **No pinned daily assignment.** `problemForDate` is `hash(date) % catalogue size`, so adding problem #7 would silently remap every past and future date. It also links every future date today.

## 3. Daily-challenge lifecycle
- **Assignment:** a `daily_challenges` row per UTC date, pinned. It is created insert-if-absent when a date is first needed, using the deterministic hash over the exam-eligible problems that have hidden tests. After that it never changes, so catalogue changes can't rewrite history.
- **Locked future:** only today and past dates resolve; future dates return nothing. The dark calendar's future cells stop linking, and today and past cells go to the challenge page.
- **Same for everyone:** one row per date.
- **Competitive window:** a challenge is competitive only on its own UTC day. A past day is view-and-practice only (statement plus a link to the normal practice page) and never touches the active week.
- **One attempt:** unique `(userId, challengeDate)`, so a learner can never have a second competitive attempt for one challenge.

## 4. Timed assessment rules
- **Server decides the clock:** Start inserts the attempt, setting `startedAt = now()` (database time) and `deadlineAt = startedAt + 30 minutes`. I propose 30 minutes, to confirm. The browser countdown is display only.
- **Submit rules:**
  - Submit is one conditional update `started → grading`, accepted only while `now() <= deadlineAt + 5 s` grace.
  - A modified client clock cannot extend it.
  - Duplicate or concurrent submits find the status already moved.
  - Anything past the deadline is `expired` and scores 0.
  - The client auto-submits at zero.
- **Scoring submissions:** one graded Submit, final. Run is unlimited and free but uses only the public example tests, executed in the browser as feedback, never for ranking.
- **States:** the page shows loading, not started, in progress, submitting, graded, expired and error states.
- **Hidden by construction:** the exam page is a new, small page. It doesn't render the Tracy panel, hints, replay, solution history or reference solutions at all, rather than hiding them with flags inside the 1000-line workspace.
- **Informational only:** an optional count of tab blur or paste events is stored as informational and never used for ranking. No camera, microphone, screen recording or invasive permissions.

## 5. Server-side grading: options and recommendation

| Option | Isolation | Fit | Verdict |
|---|---|---|---|
| **Vercel Sandbox** (`@vercel/sandbox`) | Firecracker microVM per run | Native to the Vercel deployment | **Recommended** |
| Pyodide in a Node serverless function | WASM in the same process; Python's `js` module reaches Node globals | None | **Reject** (not an isolation boundary) |
| Judge0 / Piston or similar | Vendor-run | Extra vendor, secrets and egress | Fallback |
| Own container (Fly.io, Cloud Run) | Strong | New infrastructure outside Vercel | Fallback |

**Verified facts about Vercel Sandbox** (docs):
- It is generally available and runs untrusted code in isolated Firecracker microVMs.
- The default image includes Python 3.14.
- `networkPolicy: 'deny-all'` blocks all egress including DNS.
- `runCommand({ timeoutMs })` kills a run with `SIGKILL`.
- `writeFiles` and `stop()` exist.
- Hobby includes 5 active-CPU hours, 5,000 creations and 10 concurrent sandboxes a month; Pro is about $0.13 per CPU hour.
- In production on Vercel, authentication is automatic through the OIDC token.
- Locally it needs `vercel link` plus `vercel env pull`, or an access token.

**The key design point is where the answers live.** The existing harness holds the expected answers in the same process that runs learner code, so a learner's code could simply read and return them. For competitive grading:
- **Only test inputs go into the sandbox.** Hidden expected outputs never leave the server.
- **A tiny stdlib runner** executes each learner call in its own subprocess with a per-case timeout, and returns only the actual outputs.
- **The Next server compares** those outputs to the hidden expected values locally.
- **Equality follows Python semantics** (for example `True == 1`).
- **Parity with practice:** the runner reuses `RUN_PROGRAM` and `buildRunRequest` so grading matches practice grading.
- **Only pass/fail and counts** are stored or returned to the browser.

**Limits and trade-offs:**
- **Hidden suites don't exist yet.** The visible tests are public, so each exam problem needs a new server-only hidden suite (edge cases and a performance case). That is real authoring work.
- **Burst capacity:** Hobby allows 10 concurrent sandboxes. Submissions are stored first and graded asynchronously, with a retry when capacity is short.
- **A grader failure never scores.** It marks the attempt `grader_error`, retried from the stored source.
- **Cheating prevention:** this prevents forged scores and answer leaks. It cannot stop a friend or an AI helping with the code.
- **Dependency and deployment:** it needs the `@vercel/sandbox` dependency, a Vercel project and plan that allow Sandbox, and the OIDC token at runtime. I cannot check the last two from here, and that part is Codex's and your deployment territory.

## 6. Leaderboard scoring and weekly reset
- **Daily score:** 1000 × (hidden tests passed ÷ total), rounded. A full pass adds a bonus of up to 100, scaled linearly by the remaining time. An unsubmitted, expired or ungraded day scores 0.
- **Weekly total:** the sum over Monday–Sunday UTC, by challenge date.
- **Tie-breakers, in order, published on the page:** higher total; more days fully solved; lower total elapsed time on solved days; earlier final scoring submission. If everything is equal, they share a rank.
- **Weekly reset:** a week starts Monday 00:00 UTC, and the week is set by the challenge date, so a Sunday 23:55 start still counts for that week.
- **Public Top 20:** the top 20 among learners with a public profile (`profileVisibility = PUBLIC` and a username), showing username and score only.
- **Private rank:** every participant sees their own rank privately, "rank X of N", even outside the top 20. No emails or internal IDs are shown.
- **History:** a standings snapshot per closed week, written once after a short grace by the existing cron slot. Until then history can be derived from graded attempts. The daily cron runs once at 15:00 UTC, which is enough for this.
- **Never shown:** source code. Nothing is estimated or fabricated.
