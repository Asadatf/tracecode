**Fixes and other one-off changes.** A fix should never wait on paperwork, so I'd sort changes by what they do to behaviour:

| Change | Spec work |
| --- | --- |
| Bug fix that restores behaviour a spec already describes | No spec edit. Add a regression test, and name the criterion in the commit (`fix(trace): … (trace-replay AC3)`). |
| Bug in a case the spec never covered | Add one line to the spec's Edge cases (or a new criterion) in the same PR as the fix. |
| Behaviour change, however small (copy, limits, flow) | Update the spec in the same PR. |
| Refactor, dependency bump, chore, CI, styling with no change to behaviour | No spec. |
| A choice with real trade-offs (library, data shape, security posture) | Write an ADR. |

`spec-check` would apply the same sorting, so a `fix:` commit that touches only internals passes. Anything that changes a contract without updating the spec gets flagged.
