| A choice with real trade-offs (library, data shape, security posture) | Write an ADR. |

**OpenRouter** is one service that gives access to many AI models from different companies through a single API key. You pick a model by name, and some models are free. Umair uses it because it has free models; that's the "free API" he mentioned.
- The app uses `nvidia/nemotron-3.5-super-vl:free` by default, which costs $0.
- A different model can be set with `OPENROUTER_MODEL` in `.env.local`, but only models the app has a price listed for.

**It isn't a general "explain anything" chatbot.** It does one narrow job, and it doesn't explain your code or why a test failed (the step-by-step replay and the hints do that, without AI).

1. **The app decides first, without AI.** From your saved activity (problems solved, failed runs, replays watched, hints used, patterns in your code) it ranks which problem you should do next, using fixed rules.
2. **Then it asks the AI to put that decision in words.** It sends that ranking plus a short summary of your stats. The AI returns:
   - a short, encouraging explanation of *why* that problem is next;
   - one concrete next step.

   These show on the dashboard as an "AI insight", which you can refresh.

**The system prompt keeps it on a tight leash.** It's in `src/server/learning/recommend-ai.ts:191`. In short, it says:
- Explain the recommendation that's already decided. Don't change it or suggest another problem.
- Only mention problems and numbers that are in the data, and invent nothing.
- Treat guesses about the learner as guesses, not facts.
- No claims about speed or complexity (no "O(n)"), and no "you've mastered X".
- Keep it short, and reply only in the given JSON format.

**The app then checks the answer.** It rejects the whole reply if the AI cites an unknown problem, uses a number that doesn't match the data, or makes a forbidden claim. In that case, or if there's no key, the AI is slow, or the free limit is used up, the dashboard just shows the plain rule-based explanation. The AI is an optional extra; nothing depends on it.

**Privacy:** it never sends your code, name, email or account IDs. It sends only problem names, counts and pattern labels.

So without an OpenRouter key you lose nothing important, just the friendlier wording.

We do keep them in an env file, just **Supabase's** env file rather than the app's. The rule is simple: **a secret lives with the program that uses it.**

| Program | Its env | Secrets in it |
|---|---|---|
| **Our Next.js app** | `.env.local` locally, Vercel env vars live | Secrets the app itself uses: `DATABASE_URL`, `SUPABASE_SECRET_KEY`, later `RESEND_API_KEY`, `OPENROUTER_API_KEY` |
| **Supabase** (a separate server) | `tracecode-local-supabase/supabase/.env` locally, the Supabase dashboard live | Secrets Supabase uses: the Google and GitHub client secrets |

Local Supabase is its own program running in Docker. It reads its own env file, just as our app reads `.env.local`. On the live site, "putting them in the Supabase dashboard" means the same thing: hosted Supabase keeps them encrypted in its own settings, which act as its env.

**Where vaults fit:** a vault (1Password, Doppler, AWS Secrets Manager, Supabase Vault) is a safe place to **store and share** secrets, for example so Umair can get them without you sending them on WhatsApp. An env file or env vars are how a **running program receives** them. Good question. Supabase's own docs recommend exactly this: keep your own "profiles" or "users" table next to theirs. There are four reasons it matters for us.

1. **`auth.users` belongs to Supabase, not us.** It lives in Supabase's private `auth` schema, holding passwords (hashed), sign-in tokens and provider data. Supabase changes it during upgrades, and you shouldn't add your own columns to it. Our app's data needs a table we control.
2. **Our other tables need something to point at.** Attempts, progress, notes and notifications all have a `userId` that must refer to a real user, and deleting a user deletes their data (`onDelete: Cascade`). Prisma, the tool that manages our database, only manages our `public` schema, so those links point at `public.users`.
3. **It keeps sign-in swappable.** The project's rule (`docs/rules/auth.md`) is that Supabase does **sign-in only**, and all app data goes through our own database code. If we ever moved to a different sign-in service, only the sign-in part would change, and every learner's progress would stay where it is.
4. **It's where app-specific info goes.** Today it holds just the ID and email. Later it can hold display name, preferences or a plan type, without touching Supabase's table.

The two stay in sync simply: **our `users.id` is the same ID as Supabase's**, as you just saw (`33a9f805…` in both). Each time someone signs in (email, Google or GitHub), `provisionUser` creates or updates their row. There's no second ID to keep matched up.

So `auth.users` answers "who is this and how do they sign in?", and `public.users` answers "what does TraceCode know about this learner?".
